# @b4run/postgres-storage

## Use this when

Use this package when a deployed B4.run application needs shared durable checkpoints, Agent Protocol threads, and permission grants across instances. Each permissions-store instance caches grants and observes another instance's writes after its next `load()`. The root accepts a structural pool for Node or edge hosts. `/node` adds `pg` connection-string convenience.

## Install and import

```bash
npm install @b4run/postgres-storage pg
```

```ts
import { createPostgresThreadsStore } from "@b4run/postgres-storage"
import { postgresCheckpointer } from "@b4run/postgres-storage/node"
```

| Surface | Runtime | Purity | Audience | Stability |
|---|---|---|---|---|
| `@b4run/postgres-storage` | edge-safe | not-claimed | application | supported |
| `@b4run/postgres-storage/node` | node-only | not-claimed | application | supported |

The edge-safe classification covers the root's import graph. It is tested on local workerd with a Neon WebSocket pool, not on every edge provider or a live Cloudflare deployment.

### Shared run admission

Sharing checkpoints alone does not serialize graph execution across replicas.
`createPostgresRunAdmission({ pool, schema?, tablePrefix?, leaseDurationMs?, heartbeatIntervalMs? })`
creates one request's ownership object. Its `pool` must back the injected
checkpointer, thread, permission and client-tool stores. Migrate every configured
store before claiming; generated Vercel/Hono output supplies this wiring and
request-scoped `RequestStores.runAdmission` automatically. A custom embedder must
provide the admission and its fenced stores together.

The default lease lasts 30 seconds and renews every 10 seconds. Both intervals
must be positive integer milliseconds and the heartbeat must be shorter than the
lease. Admission, renewal and transactional checks use the database clock. An
expired owner cannot renew or commit through its fenced pool. A process crash
leaves a lease that can expire; a new owner has a different token.

`tryAcquire(threadId)` returns false for contention. The runtime returns HTTP 409
`run_in_flight` with `Retry-After: 1`. It accepts callback results and reads the
checkpoint that decides a continuation only while owned. Normal terminal success
waits for final writes and asynchronous release; disconnected or abandoned work
retains ownership until its deferred cleanup completes. `release()` is idempotent;
`close()` also ends an underlying pool only when this admission owns it.

The fenced pool uses short transactions around individual store operations.
Explicit `BEGIN`/`START TRANSACTION`, `COMMIT`/`END`, and `ROLLBACK` are supported;
nested transactions, savepoints, control modifiers and statement batches are
rejected while owned. SQL text accepts positional parameters but rejects other
dollar syntax and backslashes; pass unrestricted data as bound values. This is a
runtime-store SQL subset, not a general SQL execution interface. Do not keep a
transaction open through model generation.

The process-local registry remains the default without shared admission. This
feature does not coordinate distributed AP cancellation, fence separately
configured memory or boot-owned approval-grant stores, or guarantee exactly-once
external tool effects. Existing managed-workspace restrictions on `requestStores`
remain unchanged.

### Migration and pool ownership

Migration state is instance-scoped. In a per-request host, migrate an unflagged cold set of every configured component, then set `assumeMigrated` only for the same database, schema, prefix, component, and current package schema. A wrong assertion fails on the first query. Checkpoint, thread, permission, client-tool, and run-admission migrations are separate.

Another process sees a durable permission grant only after that store calls `load()`. When you construct a custom permissions store, pass the resolved `mode` and config explicitly. B4.run does not overlay sibling configuration onto an already-created store.

Do not mark every store as owning one shared pool. An injected pool defaults to caller-owned and receives no error listener from B4.run. Setting `ownsPool: true` makes that store end it. A `/node` factory-created pool is owned, monitored, and closed by that store.

Schemas, table prefixes, and thread IDs organize data, but they are not tenant authorization boundaries. Rows are plaintext unless your database and infrastructure provide encryption.

## Examples and related guides

```ts
import { Pool } from "pg"
import {
  createPostgresPermissionsStore,
  createPostgresThreadsStore,
  postgresCheckpointer,
} from "@b4run/postgres-storage"

const pool = new Pool({ connectionString: process.env.DATABASE_URL })
pool.on("error", (error) => console.warn("Postgres pool error", error))
const checkpointer = postgresCheckpointer({ pool })
const threadsStore = createPostgresThreadsStore({ pool })
const permissionsStore = createPostgresPermissionsStore({ pool })
await Promise.all([checkpointer.ready(), threadsStore.ready(), permissionsStore.ready()])

// During application shutdown:
await Promise.all([checkpointer.close(), threadsStore.close(), permissionsStore.close()])
await pool.end()
```
