On June 17, Vercel introduced [eve](https://vercel.com/changelog/introducing-eve-an-open-source-agent-framework), an open-source agent framework. Its use of files and directories caught my attention: an agent has a model declaration, instructions, tools, and related capabilities in its folder.

That is an idea I care about in B4.run too. I want a developer to open an agent application and understand where its behavior comes from.

A similar file structure does not mean two frameworks are interchangeable, though. Let's look at what the structure helps us understand, then consider the runtime and integration choices behind it.

**Updated September 2026:** This post began as a response to eve's launch. The comparison below uses the linked documentation and B4.run's current application conventions. It should not be read as a complete feature comparison of the June releases.

## Goals

If you are evaluating an agent framework, I suggest starting with three questions:

1. Can my team understand and test the application code?
2. How will users interact with the agent?
3. Where will the application run, and which services will it need?

These questions are familiar from web development. Adding a model does not remove the need to answer them.

## What does a file-based agent give us?

An agent combines instructions with a model and tools. The model requests a tool call, and the runtime executes application code to perform the requested action.

Imagine a support assistant that looks up orders and checks refund policies. As a reviewer, I want to find:

- The instructions given to the assistant.
- The function that looks up an order.
- The policy used to approve a refund.
- The tests for successful and failed requests.

Files and folders give those pieces predictable locations. They also let us review a change with the tools we already use for TypeScript projects.

Vercel's launch example uses `agent.ts` for the model, `instructions.md` for instructions, and folders for tools and subagents. The [launch announcement](https://vercel.com/changelog/introducing-eve-an-open-source-agent-framework) shows that layout alongside its deployment workflow.

Here is the corresponding idea in B4.run:

```text
src/app/support/
  index.ts
  state.ts
  tools/
    lookupOrder.ts
  skills/
    refund-policy/
      SKILL.md
  subagents/
    research/
      index.ts
```

First, `index.ts` defines the parent agent. Next, `tools/` holds the route-specific functions it can call. The skill provides instructions that can be loaded when needed, and the research child handles a bounded part of the work.

I like this because the application gives us a starting point for answering “what can this agent do?” We still need to inspect shared tools, configuration, and permissions, but we can begin with the route.

## Compare the integration points

The following table focuses on a few decisions you will encounter while building an application.

| Decision | eve | B4.run |
| --- | --- | --- |
| Where do instructions live? | `instructions.md` beside the agent declaration | `systemPrompt` in the route descriptor; additional prompt memory and skills have file conventions |
| How is an agent organized? | An agent directory | A route under `src/app/` |
| How do tools declare input? | The documented tool example uses an explicit input schema | Type generation reads the TypeScript function signature |
| How do users reach it? | Channel integrations, including Slack, Discord, and GitHub | HTTP APIs and an AG-UI adapter for clients; application code connects other channels |
| Which deployment path should I examine? | The documented Vercel deployment and its services | The Node/Docker, LangSmith, and other target-specific B4.run deployment guides |

The eve details here come from its [announcement](https://vercel.com/changelog/introducing-eve-an-open-source-agent-framework) and [documentation](https://vercel.com/docs/eve). B4.run's [Tools](/docs/tools), [AG-UI](/docs/ag-ui), and [Deployment](/docs/deployment) guides explain its corresponding APIs.

A table is only a starting point. Let's unpack the decisions that affect the rest of the application.

## Tool types

In B4.run, a tool's TypeScript input type is used to generate the schema shown to the model. For example:

```ts
export const description = "Format a greeting for a customer."

export default async ({ name }: { readonly name: string }) => {
  return `Hello, ${name}!`
}
```

The function accepts a `name` string. Type generation derives that required input from the signature, so we do not write a second schema for the same argument.

This is useful when your team already relies on TypeScript during refactoring. It reduces one source of duplication. It does not remove runtime validation of external data or application authorization; those are still part of implementing a tool correctly.

## Client integrations

A **channel** is how a person or system interacts with an agent. A browser chat, a Slack conversation, and a scheduled job can all be entry points into an application.

B4.run exposes thread-based HTTP APIs. A thread holds a conversation and its saved state. A client starts a run under that thread, receives the result or stream, and can continue the conversation later.

For browser clients, AG-UI describes events such as new text, a tool call, or an approval request. B4.run's adapter translates runtime activity into those events. The reference web client uses CopilotKit.

If you need another channel, account for the application work around the HTTP call: authenticating the sender, mapping conversations to threads, handling retries, and displaying approval requests. A framework's built-in integration can save time here, provided it fits those requirements.

## Runtime and storage

The **runtime** executes the agent and its tools. Storage retains the conversation and execution state across requests.

B4.run builds around LangGraph.js. Its runtime can retain checkpoints, threads, and permission grants using SQLite or a configured Postgres backend. Long-term memory is a separate store, so choosing Postgres for conversation state does not automatically configure the agent's memory collection.

Vercel's [eve documentation](https://vercel.com/docs/eve) describes how its deployment uses Vercel Workflows, Sandbox, AI Gateway, and related platform services. When evaluating that path, include the services in your deployment and operations plan.

For either framework, I would test the same small scenario: start a conversation, stop the application, then continue it. Next, test an approval that pauses a run and resumes after a user decision. Those exercises reveal more about the fit for your project than a “durable execution” checkbox alone.

## Tools that execute code

If an agent can run shell commands, look at where those commands execute. An approval rule decides whether an operation may proceed. A sandbox determines the environment in which it runs.

B4.run offers optional sandbox providers, including Docker and Kubernetes. Their network and filesystem behavior depends on the provider and its configuration. For example, Docker's deny-network mode and its best-effort allow-mode denylist provide different controls. The [Sandbox guide](/docs/sandbox) documents those limits.

Evaluate the actual environment your application will use. A container, a hosted sandbox, and an approved command running on the application host have different properties, even when the agent sees a similarly named tool.

## How I would evaluate the fit

I would build one small application in each candidate framework and follow it through development, testing, and deployment:

1. Add one tool that calls an existing service.
2. Write a repeatable test for a successful response and a service failure.
3. Connect the client or channel the team plans to use.
4. Add a human approval before an operation that needs review.
5. Deploy to the intended host and test continuation after a restart.

Then compare the amount of application code and operational setup each version needs. Include the team's existing knowledge of LangGraph, Vercel, TypeScript, and the services involved.

That gives you a decision based on a working example and your requirements.

## Conclusion

I am glad to see more agent frameworks give application code a predictable structure. It makes the instructions, tools, and execution easier to find and discuss.

For B4.run, the combination I value is filesystem routes, TypeScript-derived tool inputs, and the LangGraph.js ecosystem. Your choice will also depend on the clients, services, and deployment environment your team needs.

Start with the [B4.run Getting Started guide](/docs/getting-started) and the [eve documentation](https://vercel.com/docs/eve), then try the same small use case in both. A familiar file tree is a good beginning; running your application through its complete workflow will tell you much more.
