# Execution Sandbox

The execution sandbox runs workspace tools in an isolated filesystem, shell and network, away from the app's local `workspace/` directory. Add a `sandbox` key to `b4.config.ts`, and B4.run routes `readFile`, `writeFile`, `editFile`, `listDir` and `runBash` through a `SandboxProvider`. B4.run ships a Docker reference implementation, and other providers can implement the same interface. The built-in providers hash an application scope with each logical thread ID to name their resources. Your application still authorizes thread access.

The sandbox is the third of four [access controls](/docs/access-control), after [tool scoping](/docs/tools#scoping-a-routes-tools) and [permissions](/docs/permissions) and before [guarded delegation](/docs/subagents#delegation-policy). It limits what an allowed call can touch.

## Quickstart

Install Docker, start its daemon, and add the package:

```bash
npm install @b4run/sandbox
```

Then configure `dockerSandbox` in **b4.config.ts**:

```ts title="b4.config.ts"
import { config } from "@b4run/cli"
import { dockerSandbox } from "@b4run/sandbox"

export default config({
  sandbox: {
    provider: dockerSandbox({ scope: "my-app", image: "node:24-slim" }),
    network: { mode: "allow", denylist: ["169.254.169.254"] },
    env: { NODE_ENV: "production" },
    resources: { memoryMb: 512, cpus: 1, timeoutMs: 120_000 },
    idleTimeoutMs: 600_000,
  },
})
```

Without a `sandbox` key, workspace tools keep using the app's local `workspace/` directory. `b4 check` validates the configuration and calls the provider's optional `preflight()`. For Docker, that confirms the daemon is reachable, so a stopped daemon fails before the first agent turn.

## What's isolated

- **Filesystem:** workspace file tools use a sandbox volume, not the host filesystem.
- **Shell:** `runBash` executes in the sandbox and is still subject to permissions.
- **Network:** `sandbox.network` states a portable policy. Enforcement depends on the provider.
- **Environment:** only `sandbox.env` entries are injected. The host environment stays on the host.
- **Resources:** `memoryMb` and `cpus` cap compute, and `timeoutMs` caps one command.

## Lifecycle

B4.run passes the thread ID to the provider and reuses the resulting sandbox across turns:

- `acquire()` creates or reattaches the thread's live compute and workspace.
- Idle reap and `release()` discard warm compute but keep the workspace volume.
- A later turn reattaches that volume.
- Thread deletion calls `destroy()`, which removes both compute and workspace data.

Storage is named from a stable hash of the application scope and thread ID, so a provider can reattach it after compute is released. Provider retention can shorten this lifecycle: an operator-owned cleanup policy may delete released storage before the thread is deleted. See [Kubernetes Sandbox](/docs/sandbox/kubernetes) for that provider's reaper. Subagents share their parent's thread, so they share its sandbox too.

### Application scope

Both providers require `scope`, a stable application and environment identifier such as `code-fixer-production`. Scope and thread ID are hashed together for every container, volume, Pod, PVC and NetworkPolicy name. Case and punctuation are significant. Handles and tool context keep the original logical thread ID.

Use a different scope for each independent application or environment. Keep it stable across restarts and deployments, and don't generate it on startup. Replicas using the same scope address the same storage, but scope adds no cross-process coordination. It is not authentication: authorize access to each thread and keep mutually untrusted workloads behind separate daemon or namespace boundaries.

<Callout type="warn" title="Breaking change: workspace resource names">
  Upgrading from providers without scope changes all resource names. Old storage is not automatically reattached, migrated, or deleted. Export any data you need before upgrading and clean up the old resources yourself. Changing scope also selects different storage. Missing or blank scopes fail immediately.
</Callout>

### Per-thread workspaces

Most apps give every thread the same initial workspace. When threads need different starting points (say, one repository pin per work order), make `sandbox.workspace` a function of the thread:

```ts title="b4.config.ts"
export default config({
  sandbox: {
    provider: dockerSandbox({ scope: "factory", image: "factory-builder:pinned" }),
    workspace: async ({ threadId, metadata, signal }) => {
      const task = String(metadata.task ?? "")
      signal.throwIfAborted()
      if (!/^[a-z0-9-]+$/.test(task)) throw new Error(`thread ${threadId} names no task`)
      // `include` is the exact list of files under `directory`, not a set of paths to admit.
      return {
        source: { directory: `tasks/${task}`, include: ["TASK.md", "src/index.ts", "src/lib.ts"] },
        baseline: "git",
      }
    },
  },
})
```

Let's quickly review:

- `include` must name every file under `directory`. Narrow the capture with `directory` and `excludeDirectories`, not with a partial `include` list.
- The resolver runs once, when the thread is first admitted, and B4.run records its result by digest. Every later turn reads the record. Deleting the thread deletes the record, so a thread ID reused after deletion is resolved again.
- A resolver that captures from the app root (`directory: "."`) must exclude `.b4` with `excludeDirectories`, because the installation's own state lives there. An excluded directory must already exist when the capture runs. That's always true at admission, but not for a static definition in a fresh clone at build time.
- The resolver runs inside the thread's admission critical section. Honor `signal` and return promptly, because a hung resolver holds that thread's admission open.
- Thread metadata is client input, so validate it as the example does.

`b4 check` reports a resolver as "managed workspace is resolved per thread", and a built app carries a resolver marker instead of captured source.

## Security hardening

The Docker provider applies these defaults:

| Control | Docker mechanism |
| --- | --- |
| Linux capabilities | `--cap-drop ALL` |
| Privilege escalation | `--security-opt no-new-privileges` |
| Process count | `--pids-limit 512` |
| Root filesystem | `--read-only`, with writable `/tmp` and `/run` tmpfs mounts |
| User | `--user 1000:1000`, with `HOME=/workspace` |
| Orphan reaping | `--init` (always on; not policy-controlled) |

`--init` installs a real PID 1 in the session container. Without it, nothing reaps a descendant orphaned by a cancelled or timed-out command. The zombie holds a `--pids-limit` slot for the life of the container, and process-tree termination looks like it failed because the pid is still signalable.

The portable `security` policy exposes `dropAllCapabilities`, `noNewPrivileges`, `readOnlyRootFilesystem`, `runAsNonRoot` and `pidsLimit`. You can override each one for a compatible image, but every relaxation weakens isolation.

<Callout type="warn" title="Bake dependencies into the image">
  The default non-root user and read-only root filesystem block runtime package installs and writes outside the workspace or scratch mounts. Install system and global dependencies when you build the image.
</Callout>

### Per-command timeout

`resources.timeoutMs` bounds one `runBash` call. Docker wraps the command with GNU `timeout`, and an overrun exits with code `124`. The limit is rounded up to a whole second and applies only when configured. The sandbox image must contain the `timeout` binary. `node:24-slim`, Debian and Ubuntu include it or can install it, but minimal and distroless images may not:

```ts
sandbox: {
  provider: dockerSandbox({ scope: "my-app", image: "node:24-slim" }),
  resources: { timeoutMs: 120_000 },
},
```

## Network policy

The portable policy has two modes:

- `{ mode: "deny" }` asks the provider for default-closed egress. Docker enforces this with `--network none`.
- `{ mode: "allow", denylist?: [...] }` leaves egress open and lists hosts to block.

When you omit it, the policy defaults to allow mode with `169.254.169.254` in the denylist. Docker's allow-mode denylist is best-effort, not a firewall. Use an egress proxy or another provider when you rely on host-level filtering for security. Docker deny mode is the stronger option because `--network none` removes network access entirely.

Providers map the policy differently, so read the provider's guide before assuming Docker behavior applies elsewhere.

A subagent runs under its parent's thread, so the coordinator and all of its subagents resolve to the same sandbox and workspace.

## Reading a thread's workspace from another process

A trusted process outside the runtime can read a thread's workspace without touching that thread's live sandbox. For example, a controller that dispatched work to an agent can check what came back:

```ts
import { dockerSandbox } from "@b4run/sandbox"
import { inspectWorkspace, withWorkspaceReader } from "@b4run/workspace"

// The same scope and image the worker runtime uses.
const provider = dockerSandbox({ scope: "my-app", image: "node:24-slim" })

const produced = await withWorkspaceReader(provider, { threadId, signal }, (reader) =>
  inspectWorkspace(reader, {
    excludeRootDirectories: [".git"],
    maxTotalBytes: 2 * 1024 * 1024,
  }),
)
```

`withWorkspaceReader` opens the reader, hands it to the callback, and always closes it. Call `provider.openWorkspaceReader()` directly only if you need to manage `close()` yourself.

A reader is safe while a worker is mid-thread or idle between turns. It never calls `acquire()`, so the worker's compute stays put. It reads the workspace through a separate, ephemeral, networkless container that mounts the workspace read-only. Writes fail at the kernel, and the reader object has no write method and no shell, so nothing on it can express a mutation. Reads after `close()` are refused up front, so you never see a confusing container error.

`openWorkspaceReader` is optional on `SandboxProvider`, so check for it or let `withWorkspaceReader` raise. `dockerSandbox` implements it. `kubernetesSandbox` doesn't. Its per-thread storage is a `ReadWriteOnce` PersistentVolumeClaim, which a second Pod can mount only if it happens to land on the same node. A capability that works by accident of scheduling is worse than a missing one.

Two things to know before you use it:

- **It is not an authorization boundary.** It's a host-side API for a caller you already trust, one that holds the provider and with it the container runtime. Naming a thread ID proves nothing about ownership, so gate access to the calling process. Since it's neither an agent tool nor an HTTP endpoint, no route, permission or thread-access policy is consulted.
- **The reader runs as uid/gid `1000:1000` by default**, matching the owner of a workspace produced under the default security policy. A thread that set `security.runAsNonRoot: false` produced root-owned files. Pass the same value as `runAsNonRoot` on the input so the reader can read restrictive modes.

An inspection is not an atomic snapshot. Quiesce the writer (read after the turn ends) or revalidate before acting on the inventory.

Docker readers are labelled `b4.sandbox.reader=<resource id>` and are removed on `close()`, including when the open itself fails. If `close()` can't remove the container, it raises and you can retry it. Deleting a thread leaves its readers in place, so a reader that's never closed outlives the thread. An operator finds leftovers by that label: `docker ps -aq --filter label=b4.sandbox.reader`.

Reading needs a workspace volume with a host-visible backing path, which the default local volume driver provides. A volume that reports none is rejected. A named-volume mount would have silently recreated a deleted workspace instead of failing.

## Custom providers

Implement `SandboxProvider` to integrate a microVM, cloud sandbox or another isolation backend:

```ts
import type { SandboxHandle, SandboxPolicy } from "@b4run/sandbox"

export interface SandboxProvider {
  readonly name: string
  acquire(input: {
    readonly threadId: string
    readonly policy: SandboxPolicy
    readonly signal: AbortSignal
  }): Promise<SandboxHandle>
  release(threadId: string): Promise<void>
  destroy(threadId: string): Promise<void>
  preflight?(): Promise<{
    readonly ok: boolean
    readonly detail?: string
    readonly warnings?: readonly string[]
  }>
  openWorkspaceReader?(input: OpenWorkspaceReaderInput): Promise<SandboxWorkspaceReader>
}
```

Let's quickly review:

- `acquire()` must be idempotent for a thread.
- `release()` drops warm compute and keeps workspace data. `destroy()` removes both.
- `preflight()` can fail a configuration before runtime, or return `warnings` when the provider can't prove a requested control.
- `openWorkspaceReader()` is optional. Implement it only if your backend can attach a thread's workspace storage a second time. It must not create, replace, start or stop the thread's sandbox, it must make writes impossible, and it must reject when the thread has no workspace storage. An empty view would tell a verifier "produced nothing" when the real answer is "does not exist".

Validate the implementation with the shared conformance suite:

```ts
import { runProviderConformance } from "@b4run/sandbox/testing"
import { describe } from "vitest"
import { myCloudSandbox } from "./my-cloud-sandbox.js"

runProviderConformance({
  name: "my-cloud-sandbox",
  makeProvider: () => myCloudSandbox({ apiKey: process.env.MY_SANDBOX_KEY! }),
  describe,
})
```

The suite checks acquire and reattach idempotency, per-thread isolation, release-versus-destroy storage semantics, and numeric command exit codes. If the provider implements `openWorkspaceReader`, it also checks that a reader sees what the thread produced, exposes no write or shell surface, rejects a thread with no storage, and leaves the thread's sandbox readable, writable and executable afterwards. Providers without the capability skip that block.

## Testing your agent

Use `fakeSandbox()` for deterministic tests that need the provider contract without Docker:

```ts title="b4.config.ts (test)"
import { config } from "@b4run/cli"
import { fakeSandbox } from "@b4run/sandbox/testing"

export default config({
  sandbox: { provider: fakeSandbox() },
})
```

This exercises B4.run's per-thread acquisition, reuse and subagent wiring. Provider conformance and gated integration tests cover the real isolation backend.

## Verifying the full arc (end-to-end)

Two gated CI lanes exercise a built B4.run app, a real provider, command output inside the isolated workload, and cleanup after thread deletion:

- `sandbox-docker-e2e` runs the app as a container and drives `dockerSandbox` to create a sibling container.
- `sandbox-k8s-e2e` deploys the app and drives `kubernetesSandbox` to create a sandbox Pod. Setup is in [Kubernetes Sandbox](/docs/sandbox/kubernetes).

Both use a mocked model, assert that the in-sandbox process runs as UID `1000`, and confirm compute and storage are removed on thread deletion. They run only when `B4_TEST_SMOKE_E2E=1` is set.

Only a B4.run runtime entry (`b4 dev`, `b4 start` or the Node build target) constructs the configured sandbox. LangSmith platform artifacts run without it. Edge targets reject incompatible filesystem and sandbox capabilities, so workspace tools never run there without isolation. See [Deployment Options](/docs/deployment).

## What it is and isn't

**It is** a filesystem and process boundary keyed by the provider's derived thread resource name. It also gives you explicit environment injection, CPU and memory controls, provider-specific network policy, a workspace lifecycle that outlives warm compute, and hardened Docker defaults: a non-root user, dropped capabilities, no privilege escalation, a read-only root filesystem and a process-count limit.

**It is not** authorization, tool selection, or a guarantee against container-escape vulnerabilities. Tool scoping and permissions are separate controls. Docker's allow-mode denylist is best-effort, and container isolation is weaker than a microVM. For hostile multi-tenant workloads, implement a stronger provider behind the same `SandboxProvider` interface and validate its controls against your threat model.

Kubernetes maps the same policy to different mechanisms and limitations. Treat [Kubernetes Sandbox](/docs/sandbox/kubernetes) as the source of truth for that provider.
