The code-fixer installation guide now targets source commit
`89b95af3eb660fda8a45b2b5527da6bf8a29ea8d` from `cacheplane/b4run` and published
B4 **0.11.0** packages. This record replaces the
[0.10.0 qualification](./2026-09-22-code-fixer-0.10.0-qualification.md) as the
evidence for the current guide. All runs took place on September 23, 2026.

## What changed in the example

- **Base pinned by digest.** The `Dockerfile` starts
  `FROM node:24-slim@sha256:0e0ff40c39bc087845bfb27465a0df4ea419520094bc35842ff83dd8cbe6f9b6`.
  This is the same base the 0.10.0 qualification used.
- **No pull when the base is held locally.** `sandbox:prepare` reuses an existing
  prepared tag without building. Otherwise it pulls the pinned base only if
  `docker image inspect` cannot find it. It then builds with `--pull=false`.
  `B4_CODE_FIXER_REBUILD=1` rebuilds an existing tag.
- **Content-addressed tag.** `src/project/image.ts` derives
  `b4-code-fixer:<32 hex>` from the `Dockerfile`, `.dockerignore`, and
  `sample/project/package.json` and `package-lock.json`. `sandboxImage` is that
  tag. A unit test checks two things: the context allowlist admits exactly the
  hashed files, and a one-byte change to any input changes the tag.
- **Repository suite.** `pnpm code-fixer:prepare` now prepares one image per
  historical sample through the example's own script. Before this change it wrote
  one combined image under the example's fixed tag. The replay worker and the
  evaluation cleanup read the tag of the installation they run in. The
  managed-workspace Docker tests in `@b4run/sandbox` and `@b4run/cli` find the
  prepared `cli-flags` image by its `org.b4run.code-fixer.project` label, or use
  `B4_TEST_MANAGED_IMAGE`.

## Built-server smoke

This ran once for each install. A temporary helper in the app root, outside
`src/app`, used `createAimock` from `@b4run/testing` with the guide's two
fixtures and no proxy. It started `node .b4/build/server.mjs` on loopback with the
mock base URL and a dummy key. Results were the same for both installs:

- `GET /healthz` returned 200.
- `POST /threads` returned 200 and a `thread_id`.
- `POST /threads/<id>/runs/wait` on `/fix#agent` returned 200. The response held
  the `readFile` call for `TASK.md`, its result with the text of `sample/task.md`,
  and the final fixture response.
- Before the thread was deleted, one container from the prepared image was
  running.
- `DELETE /threads/<id>` returned 204. The server and mock were stopped. No
  container from the prepared image remained.

The helper was removed afterward.

## What this does not establish

- **No observed pull of the pinned base.** The base was already held locally, so
  the pull-when-missing path did not run. Docker Desktop's registry proxy wedge was
  not reproduced. This record shows only that preparation no longer depends on a
  pull when the base is present.
- **No CI run of the code-fixer Docker lanes for #809.** The `sandbox-docker` job
  failed in the software-factory drafter test before it reached the code-fixer
  steps. That test expects `export { config } from "@b4run/core"` in the built
  CLI, which #810 changed. The code-fixer Docker lanes were run only locally, as
  recorded above. `validate` passed.
- **No test of killed-verifier cleanup in the app.** The repository suite's
  `verifier-recovery` integration test, part of `test:code-fixer:sandbox`, passed.
- No live-model repair quality and no time-to-repair measurement. No paid model
  calls were made.
- The consumer check used packed local packages, not the published registry
  artifacts. Published 0.11.0 was exercised by the archive and guide installs.
- `b4 add code-fixer` was not run against a local build of the website.
- The apt layer (`git` from Debian) is not pinned. A rebuild after the build cache
  is pruned can produce a different image under the same tag, from the same
  declared inputs.

Local logs, hashes, lockfile checks, and smoke results were kept under
