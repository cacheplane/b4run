# Software factory first live issue (sub-project 4): plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Run the factory end to end on a real issue with real models, and grade what it produces against a known right answer. Write the framework spec (what should not be the developer's job) alongside, fed by what the live run exposes.

**The issue: #714, replayed.** "A route returning undefined makes `POST /threads/:id/runs/wait` answer 500." Chosen for outcome certainty: a precise, deterministic reproduction in the issue body; a one-file fix of 29 lines in `packages/cli/src/lib/dev/runtime-fetch-core.ts` (b090ad42, #718, merged 2026-09-18); and a 202-line reference test, `packages/cli/test/runs-wait-output.test.ts`, shipped with the fix. The factory runs at **pin 765e6e16** (b090ad42^, the commit before the fix), so neither the drafter nor the builder can see the answer, and afterwards the reference test grades the factory's candidate independently of anything the factory produced. Rejected: #778 (open, needs a `testing` target, no known answer), #774 (possibly stale build output), #787's fix (no issue), and larger fixes (#689, #754: multi-package).

**What this costs, on purpose:** a `cli` target. `@b4run/cli` depends on nine workspace packages (ag-ui, core, langchain, langgraph, memory, permissions, sdk, sqlite-storage, workspace) and has 177 test files. Building it by hand is the "a lot of work" the walkthrough named; the plan records every hour of it as evidence for the spec.

**Two tracks.** Track A is the live run (Tasks 1 to 4). Track B is the spec (Task 5), started now and appended with each finding from Track A.

**Standing rules:** as the 3b plan. Worktree `.claude/worktrees/factory-live`, branch `blove/software-factory-live` off main 7c7ad3c2. No new devDependencies in example packages (a lockfile peer re-key broke `@b4run/cli` tests once). The OpenAI key is sourced from the repository's gitignored `.env` into the worker processes only; it is never printed, logged or committed.

### Task 1: Replay an issue at a pin

`factory create --issue <n> --pin <sha>` pins the work order at a given commit instead of `origin/main`: the replay mode for a fixed issue. The CLI still fetches the issue with `gh`; `resolvePin` is skipped; the pin must be a commit in the object store (`ensurePin` fetches it by sha when shallow), refused before the route otherwise. The row, the journal and the bundle record it like any pin. README and spec §6.3 as-landed. Tests: CLI with the gh stub and the offline repo (pin = a non-HEAD commit; `origin/main` not consulted); a pin not in the store with `FACTORY_NO_FETCH=1` refused.

### Task 2: The `cli` target, prepared at the replay pin

`controller/targets/cli/target.json` + `Dockerfile`, modelled on `devkit`, at default pin 765e6e16.
- **Capture:** root manifests; `packages/config-typescript`; for `cli` and each of its nine workspace dependencies: `package.json`, `tsconfig*.json`, `src`, and for `cli` also `test` and its vitest config. Exclude nothing the build needs; measure the capture's size.
- **Image:** installs the workspace dependencies for `@b4run/cli...` into `/opt/targets/cli`, as devkit's does; `imageAssertResolves` for vitest, typescript and the node types.
- **Commands:** `build` builds the dependency graph in order (`pnpm -r --filter @b4run/cli... run build`, or `tsc -b` over project references if the packages declare them: pick what works offline in the image); `test` runs a **scoped** set of `packages/cli/test` files that are hermetic and fast (the dev runtime's route and run tests, e.g. `runs-wait*`, `run-cancellation`, `runtime-fetch*`, `execute-route`), with the exclusions listed and the reason recorded. The builder's visible suite is this command; keep it under two minutes in the image.
- **Resources:** measured, not guessed (cgroup `memory.peak`, wall clock), with headroom.
- **Proof (Docker lane `target-cli.integration.test.ts`):** at pin 765e6e16 the build succeeds and the scoped suite passes; the reference test from b090ad42 (`runs-wait-output.test.ts`, applied as a file) FAILS on the pin and PASSES with the reference fix applied. That is the grading harness for Task 4.
- Record in the plan: hours spent, every trap, every field that had to be hand-derived. That list is Track B's evidence.

**As landed.** Part A first: `ensurePin` fetched a missing pin with `--depth=1` unconditionally, which on a full clone writes `.git/shallow`, shared by every linked worktree. It now passes `--depth=1` only when `git rev-parse --is-shallow-repository` says `true`; tested against a real full clone and a real `--depth 1` clone of a fixture origin. The operator repository here was already shallow (a one-line `.git/shallow` dated 2026-09-21, the pre-fix `ensurePin`), and nothing in this task unshallows it. The other `--depth` in the controller (`resolvePin`) was already plain. Then the target: `targets/cli` (`target.json`, `Dockerfile`) at pin 765e6e16, and a shipped task `tasks/cli-runs-wait-undefined` whose independent check is the reference test ported to `node:test` (the six cases and inputs of b090ad42's `runs-wait-output.test.ts`, as A1 to A6, importing the BUILT `packages/cli/dist`, since an independent check is a node-test file the verifier writes under `checks/`). About 2 hours of wall clock, more than half of it waiting on Docker (the lane alone ran 69 minutes).

- **Traps, each with its fix.** (1) pnpm writes workspace links relative (`node_modules/@b4run/core -> ../../packages/core`), which inside the sandbox resolves to the image's manifest-only copy, not the workspace where the build writes `dist/`: the Dockerfile rewrites each captured package's link to `/workspace/packages/<p>`. (2) The workspace may hold ONE environment link, at its root: `inspectWorkspace` refuses a symlink anywhere else (`Unsupported workspace entry (symlink)`), so the per-package `node_modules` the hoisted install leaves for conflicting versions cannot be linked in. They are promoted over the root's instead: cli's `commander` 15.0.0 (the root has 8.3.0), `hono` 4.13.5 (root 4.13.3) and `@hono/node-server` 2.1.1 (root 1.19.17), and core's `typescript`, which is the TypeScript 6 compiler API core's typegen imports; the root's TypeScript 7, the `tsc` every package builds with, moves aside to `/opt/targets/cli/tools` behind a `tsc` shim. (3) Writing that shim through the existing `.bin/tsc` symlink wrote into the promoted package; the link is removed first. (4) TypeScript 7's `tsc -b` builds projects that do not reference each other concurrently, so ten projects on one command line failed (cli compiled before sdk had a `dist`); `--builders 1` builds them in command-line order. (5) cli's own `build` script ends in `scripts/generate-docs.mjs`, which reads `apps/web` content, so `build` is `tsc -b` over explicit project paths, not `pnpm -r run build`. (6) A `chmod -R` in its own layer copied the 1.7 GB install up and doubled the image to 3.9 GB; it stays in the install layer. (7) The Docker VM (58 GB) filled up mid-run; the build cache and dangling images were pruned, and a concurrent session's image prune then removed this task's scratch image and `node:24-slim`. (8) The base pull wedged for 11 minutes on the devkit lane's re-prepare; killed by PID, rerun with `FACTORY_SKIP_BASE_PULL=1`. (9) **The verifier's tamper snapshot does not scale to this target.** Each snapshot is one `docker exec` per `lstat`, per read and per `listDir`, and every one of those operations first runs `ManagedWorkspaceManager.getForThread`, which re-reads the captured source bundle from the store and re-verifies the whole definition (`verifyCapturedWorkspaceDefinition`) before it reaches the cached session. So the cost of one operation grows with the capture's bytes and the number of operations grows with its files: measured at about 170 ms an operation, 4,181 execs, and 717 s for ONE session (build 3 s, suite 15 s, the rest two snapshots). The first capture (the whole of `packages/cli/test`, 512 files, 5.3 MB) ran at about 260 ms an operation. Mitigated here, not fixed: the capture carries only the scoped test files and the one helper they import (343 files, 1.9 MB), and `build` passes `--declarationMap false` (the built tree drops from 907 to 608 files), which leaves 951 files to walk. `verifierDeadlineMs` is set to cover two such sessions with headroom. A devkit verification takes under a minute; the fix belongs in the framework spec (Task 5), and this is the item Task 3's timing will feel most.
- **Hand-derived fields.** The dependency closure (`git show 765e6e16:packages/*/package.json`, walked by hand: nine workspace packages, plus `@b4run/sandbox`, a cli devDependency whose manifest pnpm needs in the image context); `capture.include` (per package: manifest, tsconfig, `src`; the eight scoped test files and `test/helpers/probe-file.ts`, found by grepping their imports); `imageContext`; the Dockerfile's `CAPTURED` list, which restates the capture's packages (the image cannot read the manifest); the build order (hand-sorted from the packages' `dependencies`, since only cli's `tsconfig.build.json` (not to sdk or workspace) and `core`'s and `memory`'s `tsconfig.json` (each to `../sqlite-storage`) declare references); `snapshotIgnore` (every package's `dist/`); `runnerConfig`; the scoped test list (by running candidates in the image); the task's 69 `immutablePaths` (generated by a script from the pin's tree: every captured path that is not on the allowed file's path); `spec.md` and the A-ids (from the issue body and the reference test's cases); and the check port.
- **Scoped suite** (`commands.test`, the builder's visible suite): `execute-route`, `run-cancellation`, `run-registry`, `runtime-fetch-parity`, `thread-access-endpoints`, `thread-access-run-endpoints`, `thread-metadata`, `threads-sse-frames`: 175 tests, all passing at the pin. Excluded: `runtime-fetch-handler.test.ts` (imports `../../testing/dist`, the `@b4run/testing` package, which is outside the capture, and drives an aimock model server); every other file of the 177 is outside the run-endpoint scope and is not captured, which is what keeps the snapshot cost above within reach. `thread-access-{boot,loader,pure,resuming}`, `static-thread-access`, `threads-attach-state` and `run-diagnostics` also pass in the image and were left out for the same reason.
- **Measured** (three runs in the prepared image, the sandbox's shape: read-only root, `/tmp` tmpfs, no network, 1536 MB, 2 CPUs): build 2.8 to 3.7 s, scoped suite 12.3 to 15.3 s, cgroup `memory.peak` 449 to 487 MB for build and suite together. Capture: 343 files, 1,912,876 bytes (framework limits: 10,000 entries, 64 MB); after the build the workspace holds 951 files, about 5 MB, inside the snapshot's 16 MB. Image: 2.07 GB (1.69 GB of it the install), built uncached in about 1.5 minutes (install 36 s, layer export 13 to 24 s, plus the base pull); `target:prepare cli` with a warm cache, 71 s.
- **Harness result.** In the image, via the verifier's own session machinery (`gradeSuite`): the reference test file from b090ad42, run beside the scoped suite, FAILS at the pin (4 of 6: the null body, the client's reading of it, the parity with `runs/stream`, the named serialization error; the falsy and ordinary-object cases pass on both sides) and PASSES with the reference fix, the scoped suite passing in the same session. **Review fixes (after the first live-run attempt).** (a) The `cli` lane is opt-in: `describe.skipIf(FACTORY_TEST_CLI_TARGET !== "1")`, the task and policy loaded in `beforeAll` so an unprepared checkout skips at collection, and `test:sandbox:cli` runs that file with the variable set. CI's `sandbox-docker` job prepares no `cli` image and has 30 minutes against the lane's ~70, so it skips there (the ci.yml comment says why; comment only, the audited workflow fixtures are unchanged). The lane now asserts A1, A2, A3 and A5 fail and A4, A6 do not at the pin, and that the scoped suite ran (over 100 passes) beside the failing reference test. (b) The Dockerfile's promotion is declared: `EXPECTED_PROMOTED="@hono/node-server commander hono typescript"`; a name promoted twice or any difference from that set fails the build, and the set is echoed (`promoted over the root's: @hono/node-server commander hono typescript`). Re-prepared at 765e6e16: `b4-factory-cli:765e6e16fec8-2268d8469b20`. (c) `target:prepare` refuses a Dockerfile whose `CAPTURED` list disagrees with `capture.include`'s packages (missing, extra or repeated). (d) `runnerConfig` for `cli` adds the root `package.json`, `.npmrc` and `pnpm-workspace.yaml` (they feed `pnpm exec` and the build); the task's `immutablePaths` already covered them. (e) **Budget vs verifier deadline.** The work order's active budget is fixed at create (`FACTORY_MAX_ACTIVE_MS`, default 1,200,000) and covers the builder's turn and verification; the `cli` target's `verifierDeadlineMs` is 3,600,000. No catalog field was added: `create` of a catalog task journals `budget_below_verifier_deadline { phase, maxActiveMs, verifierDeadlineMs, targetId }` when the budget is under twice the target's deadline, and `dispatch` (catalog or generated task, whose target is only known once its draft is approved) journals it and refuses before the key and before any thread, naming `FACTORY_MAX_ACTIVE_MS` and the value to set. So Task 3 must start the controller with `FACTORY_MAX_ACTIVE_MS=7200000` or more before `create`. A factory option, `allowBudgetBelowVerifierDeadline`, waives the refusal (still journalled) for the three tests of budget exhaustion itself, whose 1-second budgets no real target fits; the runtime's configuration never sets it. (f) `--pin <short>` must resolve to a commit it abbreviates: a hex-named branch or tag that `rev-parse` prefers is refused. (g) `ensurePin`'s label for a replay reads `Issue <n> (replay) pins <sha>`. (h) The shallow-fetch unit test now pins a commit with a parent and asserts `.git/shallow` lists it; with `pinFetchDepth` returning `[]` it fails. ### Task 3: The live run

Bring up four processes (controller, drafter, one `cli` builder at pin 765e6e16, verifier via Docker) from the README, with the key from `.env`. Then, as operator:

```
factory create --issue 714 --pin 765e6e16...
factory intake <id>                  # the drafter drafts; the controller proves the oracle
# review the draft on disk: record the review (what was checked, why it is an oracle) in the work order
factory approve-intake <id> --revision <n> --digest <sha>     # or reject-intake --note
factory dispatch <id>
factory evidence <id>
factory approve <id> --revision <n> --bundle <sha>            # or deny
```

The human gates are exercised by the session operating the run, which records its review reasoning as a journal note; the user is told it acted as the approver. Every command's output, and every surprise, is recorded as evidence in the work order (journal, evidence store) and summarised in the plan. A failure of the factory is a finding, not something to route around: fix only what blocks the run, and file everything else.

**Dispatch finding (b5), and what changed before the next run.** Work order `wo-2a67180a359c7f85` dispatched; the builder rewrote `runtime-fetch-core.ts` truncated to 670 of 3,644 lines (`... (file truncated, unchanged)`), then parked on `sed -n`, which its allow-list did not admit: `blocked / unexpected_interrupt`, its one candidate attempt spent (spec §9, finding 25). Fixed on this branch: the builder runs `non-interactive` with the drafter's read-only commands added to its list; its task prompt carries `Rules:` (edit with `editFile`, read large files in ranges with `readFile`'s `startLine`/`endLine` or `grep -n`/`sed -n`, never write elision text, run the build and test to confirm, and the commands it may run); `FACTORY_MAX_CANDIDATE_ATTEMPTS` (default 2) and `factory retry <id>` return a candidate-blocked row to `received` for a fresh builder thread; the assembly refuses an elided or halved file as `candidate_rejected` before verification. **The next run depends on the framework commit** that adds `editFile` and ranged `readFile` to the workspace capability: this branch carries it before the next dispatch, since the prompt names both. Before it: regenerate the builder's target file (`factory builder-target --target cli --out …`), since the new allow-list lives there, and restart the builder. `wo-2a67180a359c7f85` was created with `maxCandidateAttempts: 1` and has spent it (migration 5 backfills `candidateAttempts: 1` from its committed dispatch), so `retry` refuses it by design and the registry is not hand-edited: the run cancels it and creates a new work order (`create --issue 714 --pin 765e6e16…`, intake, approve-intake, dispatch), which gets two attempts.
