# Flight Planner Web UI

B4.run's navlog demo, a VFR flight planner, ships with a [CopilotKit](https://docs.copilotkit.ai) web client that talks to the server over [AG-UI](/docs/ag-ui). Let's walk through how it's wired. The client is a workbench, not a chat widget. CopilotKit's stock `<CopilotChat>` sits in the middle column, between a sidenav of threads and the route map, inside B4.run's `<B4Activity>`, so the streamed brief, the turn's plan, subagent and tool steps, and the approval card all appear in message order, while the map, its route bar, and the navlog sheet read the same turns from outside the chat.

This recipe covers the application wiring. For the endpoint, events, threading, and interrupt outcomes, see [AG-UI and Web Clients](/docs/ag-ui).

## What you'll build

The demo lives in `examples/navlog`: a B4.run server (`server/`) and a Next.js CopilotKit client (`web/`). The client provides:

- **Sidenav:** "New plan", the list of threads (each titled from its first user message), and Memory, which opens Memory mode with a count of the candidates waiting; the sidebar collapses to an icon rail.
- **Chat + report:** the agent's structured answer, rendered as brief components (bottom line, route, watch-for items, key numbers, assumptions, numbered citations) in `<CopilotChat>`, with B4.run's chat slots (`useB4ChatSlots`) swapped in. A thread saved before the brief kit renders its markdown answer as before.
- **Activity:** one `TurnActivity` per turn: a summary line, then the plan, the `weather` and `performance` subagents (nested, with their own plan and tool steps), and each tool call as a step. `computeNavlog` and `renderChart` get their own opened views.
- **Map and route bar:** the planned route, a dashed draft of the route you are typing, and a marker panel with each airport's METAR and TAF. See [Type a route on the map](#type-a-route-on-the-map).
- **Navlog sheet:** the legs, the weather by role (origin, en route, destination), the totals and flight plan, and the brief, in four tabs. The map and the sheet are derived from the activity turns (`useB4ActivityContext`), not from a second subscription.
- **Suggestions:** three discovery prompts on the empty chat.
- **Permissions:** the kit's `ApprovalCard` owns approve and deny, rendered in the chat where the run stopped.
- **Input:** `<CopilotChat>`'s own input, with an image attachment when the route's model takes one. It waits while an approval is open.
- **Media:** images, audio, video, and documents in user messages and tool results, plus a notice for each part the model never saw.

The activity steps only display progress. Interrupts are resolved through the standard AG-UI fields described on the protocol page.

The Workbench also reviews durable memory. A small panel reaches B4.run through an allowlisted, same-origin proxy. See [Approve memory candidates](#approve-memory-candidates) below.

## Connect the client to B4.run

The Next.js runtime route registers a `B4HttpAgent`, an AG-UI `HttpAgent` that also reports the route's [capabilities](/docs/ag-ui#capabilities), pointed at the encoded B4.run assistant id. Register it under CopilotKit's `default` agent id so every hook binds without per-component wiring:

<CodeGroup>

```ts title="examples/navlog/web/app/api/copilotkit/[...path]/route.ts"
import { B4HttpAgent } from "@b4run/ag-ui/client"
import { createB4AgentRunner } from "@b4run/ag-ui/copilotkit-runtime"
import {
  CopilotRuntime,
  createCopilotRuntimeHandler,
  InMemoryAgentRunner,
} from "@copilotkit/runtime/v2"
import { briefJsonSchema } from "../../../brief/kit"

export const runtime = "nodejs"
export const dynamic = "force-dynamic"

const b4Url = process.env.B4_SERVER_URL ?? "http://127.0.0.1:3002"
const agUiUrl = `${b4Url}/agui/${encodeURIComponent("/navlog#agent")}`

const handler = createCopilotRuntimeHandler({
  runtime: new CopilotRuntime({
    agents: { default: new B4HttpAgent({ url: agUiUrl, responseSchema: briefJsonSchema }) },
    // Restores a thread on `connect` from B4.run's storage.
    runner: createB4AgentRunner(InMemoryAgentRunner, { url: b4Url }),
  }),
  basePath: "/api/copilotkit",
})

export const GET = handler
export const POST = handler
```

```tsx title="examples/navlog/web/app/page.tsx"
// Excerpt: the provider tree. Thread state and its handlers live in the same
// file, over `app/lib/thread-source.ts`.
<CopilotKit runtimeUrl="/api/copilotkit" useSingleEndpoint={false} defaultThrottleMs={100}>
  <CopilotChatConfigurationProvider threadId={activeThreadId}>
    <DemoSuggestions />
    <AppShell
      threads={threads}
      activeThreadId={activeThreadId}
      onSelectThread={handleSelect}
      onCreateThread={handleCreate}
      onUserMessage={handleUserMessage}
    />
  </CopilotChatConfigurationProvider>
</CopilotKit>
```

</CodeGroup>

The catch-all route is required. It exposes CopilotKit's V2 REST and SSE paths under `/api/copilotkit/*`. Setting `useSingleEndpoint={false}` makes the browser start with `GET /api/copilotkit/info` rather than send the legacy method envelope to the base URL. Only the B4.run server has `OPENAI_API_KEY`. The web runtime holds no model credential.

<Callout type="warn" title="Register the agent as default">
  CopilotKit hooks that omit an `agentId` resolve the id `default`. Register the
  B4.run agent under that id, or set the same explicit id on every consumer.
</Callout>

Two pieces of that tree matter most, plus the suggestions:

- `defaultThrottleMs={100}`: the re-render throttle defaults to *unthrottled*, and a full planning run streams hundreds of events, which pegs the renderer.
- `CopilotChatConfigurationProvider`: `CopilotKit` does not provide one (`<CopilotChat>` and `<CopilotSidebar>` did). Without it, every thread-aware hook falls back to the agent's own auto-minted thread, and selecting a thread in the sidenav would change nothing.
- `<DemoSuggestions />` renders nothing. It publishes the starter prompts into CopilotKit's suggestion registry, and `<CopilotChat>` shows them on an empty thread.

## Render the brief as structured UI

The navlog answer is JSON, not markdown. The kit lives in `examples/navlog/web/app/brief/`: `schema.ts` declares each component's props with hashbrown's `s` builder, `components.tsx` exposes the React components (`BottomLine`, `RouteSummary`, `WatchFor`, `KeyNumbers`, `Assumptions`, `Citations`, `Prose`) with `exposeComponent`, and `kit.ts` derives the JSON Schema with `createUiJsonSchema` from `@hashbrownai/core`. The runtime route hands that schema to `B4HttpAgent({ responseSchema })`, which puts it in every run's `forwardedProps.responseSchema`. The server's `b4.config.ts` allows that one key on the navlog route (`clientForwardedProps: { "/navlog": ["responseSchema"] }`), and B4.run binds it to the model's final answer, so tool-calling turns are unaffected and the last message is `{ "ui": [...] }`.

In the browser, `BriefRenderer` parses the streaming JSON with `useJsonParser` against the kit from `useUiKit` and renders each component as it completes, in the chat and in the sheet's Brief tab. Live replies are always structured, because the route sends the schema on every run; a question or a filing confirmation is a single `Prose`. Only a thread saved before the kit has a markdown answer, and it falls back to the markdown renderer.

## The workbench shell

`AppShell` is the only component that talks to the agent. It calls `useAgent()` with no arguments. That unscoped form takes its thread from the surrounding chat configuration, so `<CopilotChat>`, `B4Activity`'s interrupt handling, `useSuggestions`, and the shell all resolve the same agent and thread.

The workbench lives inside `<B4Activity key={threadId}>`. The key matters: B4Activity's pending approval card is cleared only by a new run, so an activity that outlived a thread switch would show the previous thread's approval on the next one. The key also restarts the turns from empty and remounts the chat, which connects the new thread.

```tsx title="examples/navlog/web/app/components/NavlogChat.tsx"
// Inside B4Activity: the stock chat with B4.run's slots.
const slots = useB4ChatSlots()
<CopilotChat threadId={threadId} messageView={slots.messageView} input={input} attachments={attachments} />
```

`useB4ChatSlots` renders each turn as a `TurnActivity` and a parked interrupt as an `ApprovalCard`. The example's `NavlogChat` adds echo-free prose, named input controls, and the image attachment below. `renderStep` on `B4Activity` (`app/components/StepViews.tsx`) gives `computeNavlog` a one-line totals view with a link to the sheet, and `renderChart` its image.

Run failures still need a subscription. `copilotkit.runAgent` does not reject when a run fails. It catches, emits an error, and resolves normally. Failures surface through `copilotkit.subscribe({ onError })`, which the shell turns into a banner above the chat.

Threads are local to the browser. B4.run's server can create and fetch a thread by id, but it has no endpoint to list threads. So the sidenav keeps its own list in `localStorage` behind a `ThreadSource` interface (`examples/navlog/web/app/lib/thread-source.ts`), and the app skips CopilotKit's `useThreads`. The list holds ids, titles and recency only.

The map and the sheet sit outside the chat but inside `B4Activity`. `useB4ActivityContext()` returns the same turns the chat renders, and pure selectors (`app/lib/navlog-selectors.ts`, `weather-selectors.ts`) pick the latest `computeNavlog` result and `weather` brief from them.

### Restoring a thread

`<CopilotChat>` calls `connect` when it mounts, and the runtime route's runner (`createB4AgentRunner`) answers it by replaying `GET /threads/:id/events` from B4.run's checkpoints as AG-UI events, so a restored thread and a live one go through the same path: the chat messages, the turns, and a parked approval all come back, with the media the thread carried. The browser never reads thread state itself, so the proxy has no thread routes. A brand-new thread has nothing to replay and restores as an empty chat. See [Restoring a conversation after a reload](/docs/ag-ui#restoring-a-conversation-after-a-reload) for the runner and the per-request identity it needs.

To restyle the app, edit `examples/navlog/web/app/theme.css`. It defines the palette as CSS variables and re-exports it as Tailwind tokens through `@theme inline`. That's why the app's utilities read `bg-wb-surface`, `border-wb-border`, and `rounded-wb`.

## Type a route on the map

A pilot who already knows the route can type it instead of writing a request. The route bar sits across the top of the map (and the phone's Map tab, which opens before any plan exists):

```text
[KPAO] → [SNS] → [KSBA]  add waypoint…  5500 ft  1400Z  231 nm  [Replan]
```

Each waypoint is a pill with a remove button: airports in ink, navaids in cobalt. The input is a combobox. Typing searches identifiers and names (an identifier or local-code prefix first, then a name substring), and the list shows up to 8 matches with the kind, such as `VORTAC 117.30`. Enter, Tab or space adds the highlighted match, so typing `KPAO SNS KSBA` with a space after each token builds the route. Backspace in an empty input removes the last pill.

The search reads a bundled snapshot, not a live service. `GET /api/waypoints?q=<text>` (`app/api/waypoints/route.ts`) searches `web/data/waypoints.json` on the server with `searchWaypoints` (`app/lib/waypoint-search.ts`), so the snapshot is never shipped to the browser. It answers `{ results, snapshot }`, where `snapshot` is the data's date. The handler applies the same origin, visitor and rate-limit guard as the other proxy routes and truncates `q` to 32 characters. The data comes from [OurAirports](https://ourairports.com/data/), which is public domain, and the open list says so: "Waypoints: OurAirports `<date>`, not for navigation".

Each waypoint draws on the map as soon as it's added. A draft that differs from the planned route is a dashed line, the planned route stays solid with its markers and heading labels, and the bar shows the draft's great-circle distance. The altitude field takes 1000 to 17500 ft. The departure field is passed through as typed, because the server's `resolveDeparture` accepts `1400Z`, `tomorrow 1400Z` or an ISO instant.

The button reads **Plan** before the first navlog and **Replan** after it. It is enabled with at least 2 waypoints, a valid altitude and no run in progress. It sends one ordinary chat message through the same agent the chat uses, built by `replanMessage` (`app/lib/route-draft.ts`):

```text
Plan KPAO → SNS (VORTAC) → KSBA at 5500 ft, departing 1400Z.
```

A navaid carries its type in parentheses, which tells the agent to resolve it with `lookupNavaid` instead of `lookupAirport`. The agent then plans as it would for a typed request. When the new navlog arrives, the bar resets to the planned waypoints, altitude and departure, so the plan wins over an unsent draft. While the departure field is untouched, it shows the plan's departure as `HHMMZ` and Replan sends the plan's ISO instant.

### Weather on the map and in the sheet

The map carries no weather chips. Airport markers keep their flight-category color, and the en-route reporting stations from the latest `findRouteStations` result draw as small grey markers. Airport and station markers are buttons: clicking one opens a panel in the map's corner with the identifier, the category now and at the ETA, and the raw METAR and TAF from the weather brief. Escape or the close button dismisses it. Navaid markers are labels only.

The navlog sheet's tabs are **Legs · Weather · Totals & plan · Brief**. The Weather tab (`app/components/WeatherTab.tsx`) groups the brief's airports by role (`app/lib/weather-roles.ts`):

- **Origin**, **En route** and **Destination**, each airport as a card with its category now and at the ETA and the raw METAR and TAF, or "No report in the brief". En route lists intermediate airports and stations by distance along the route ("98 nm along"), or says "No reporting stations within 25 nm of the course."
- **Winds aloft**, one line per leg.
- **Advisories**, the hazard chips, plus one chip for advisories outside the flight window.
- **Forecast horizon**, when the brief has a note.

Print includes the Weather tab's content after the legs.

## Attach an image

The attach control appears only when the route's model takes an image. `AppShell` reads that from the route's [capability document](/docs/ag-ui#capabilities):

```tsx title="examples/navlog/web/app/components/AppShell.tsx"
const capabilities = useCapabilities()
const canAttachImages = capabilities?.multimodal?.input?.image === true
```

There is no browser call to make here. In the browser, the agent is CopilotKit's runtime proxy, and it carries what the runtime's `/info` sync fetched through `B4HttpAgent.getCapabilities()`. `useCapabilities()` returns `undefined` until that handshake lands, which keeps the control hidden until then.

`NavlogChat` hands `<CopilotChat>` an `attachments` prop with `enabled: canAttachImages`, the accepted image types, and a size cap. The chat reads a picked file into an inline `image` part and sends it with the message; a text-only turn stays a plain string.

```tsx title="examples/navlog/web/app/components/NavlogChat.tsx"
const attachments = {
  enabled: canAttachImages,
  accept: ATTACHABLE_IMAGE_TYPES.join(","),
  maxSize: MAX_ATTACHMENT_BYTES,
  onUploadFailed: (failure) => setAttachNotice(attachmentFailureText(failure)),
}
```

It accepts PNG, JPEG, GIF and WebP images, the types OpenAI's vision input takes, and refuses any file over 4 MB with one dismissible line above the chat. The cap matters because every turn sends the whole conversation to `/agui`, whose request body limit is 8 MiB, so one large image would break every turn after it.

### Media in the chat

Tool steps draw their media with `app/components/MediaParts.tsx` (user messages carry theirs through `<CopilotChat>`): an `<img>` for an image, the native players for audio and video, a download chip for a document, and a chip naming the handle for a provider `file` source, which the browser can't load. A `url` source is loaded only when it's `http(s)`, because tool results are model-driven.

Each part's MIME type has to match what the part claims to be. An image part whose type isn't `image/*` renders as a chip, and so does audio or video with the wrong type. Only PDF, CSV, Markdown and plain-text documents get a download link, and the downloaded file is named from the type (`document.pdf`), never from the part's filename, which is shown only as the label.

A tool result's media arrives on the step as `parts`, live and after a restore, so `ChartStepView` (`app/components/StepViews.tsx`, registered for `renderChart` through `B4Activity`'s `renderStep`) draws it inside the opened step with `MediaParts`.

### Parts the model didn't see

When the model or its provider can't take a part, B4.run drops it and emits a `CUSTOM` event named [`b4.content_parts_dropped`](/docs/ag-ui#multimodal-content). `AppShell` subscribes with `onCustomEvent` and shows each event as a muted line in the chat column above the conversation, such as `1 content part was not sent to the model: image (tool_result_media_unsupported)`.

CopilotKit keeps no record of `CUSTOM` events, so the notices live only in the shell's state. Switching threads clears them, and a reload or a restored thread doesn't bring them back.

### Media after a restore

The replay carries media. A user message that held an attachment comes back as AG-UI content parts, and a tool that returned parts keeps the full list in the tool message's `additional_kwargs.b4_content_parts`, which the replay sends as the tool result's parts. The UI shows what the tool produced, even where the model's own copy held only text.

A user image the adapter dropped is a different case. It never reached the model, so it isn't in the checkpoint, and it doesn't come back when the thread is restored.

### A chart the model doesn't see

The navlog server ships `renderChart` (`server/src/tools/renderChart.ts`). Given a title and up to 12 `{ label, value }` pairs, it returns two parts: a one-line text summary and an inline SVG bar chart.

```ts title="examples/navlog/server/src/tools/renderChart.ts"
return [
  { type: "text", text: summary },
  { type: "image", source: { type: "data", value: base64(svg), mimeType: "image/svg+xml" } },
]
```

The user sees the chart in the opened `renderChart` step. The model, `gpt-5-mini`, sees only the summary, because media in a tool result never reaches an OpenAI model. So every `renderChart` call also produces a dropped-part notice. That's expected: the notice is telling you the truth about what the model saw.

## Render plan and subagent activities

The navlog example gets the plan and the subagents from `B4Activity`: each turn's `TurnActivity` shows the plan as a step and nests the `weather` and `performance` subagents with their own plan and tool steps, from the same AG-UI events. Choose **Plan a flight** on the empty chat to watch them update before the brief.

A client that doesn't use `B4Activity` gets the same view from the same events. `useB4Turns(agent)` from `@b4run/ag-ui/react/copilotkit` (or `reduceTurns` from `@b4run/ag-ui/view`, with no React) folds the agent's event stream into turns, and `TurnActivity` from `@b4run/ag-ui/react` renders one:

```tsx
import "@b4run/ag-ui/styles.css"
import { useB4Turns } from "@b4run/ag-ui/react/copilotkit"
import { TurnActivity } from "@b4run/ag-ui/react"
import { useAgent } from "@copilotkit/react-core/v2"

function Activity() {
  const { agent } = useAgent()
  const { turns } = useB4Turns(agent)
  return turns.turns.map((turn) => <TurnActivity key={turn.runId} turn={turn} />)
}
```

The plan is a step in its turn, "Made a plan · 2 of 4 done", with the checklist inside. A subagent is a step too, "Asked weather" over the subagent's description, with the child's own plan and tool steps nested under it. The stylesheet carries no inline styles, so without that import the kit renders as bare markup. To restyle it, override the `--b4-activity-*` custom properties in your own CSS, as the navlog example does in `app/theme.css`.

React and `@copilotkit/react-core` are optional peer dependencies of `@b4run/ag-ui`, and only the `./react` and `./react/copilotkit` subpaths need them. A server that uses the root or `./sse` entry installs nothing extra.

Plan snapshots replace `b4:plan:${runId}` (the root agent's) or `b4:plan:${call_id}` (a subagent's, tagged `subagentRunId`) and carry the complete todo list; the plan step shows every todo.

The plan activity is the whole presentation of `writeTodos`: when a `writeTodos` call produced its activity, B4.run's AG-UI adapter emits no tool call/result events for that call. A `task` call is an ordinary tool call, and the turn shows it as the subagent step it starts.

If the plan activity cannot be produced (no tool-call id, a malformed payload), the adapter fails open and the ordinary tool events survive; the view still places a plan step for the call, empty until a snapshot arrives.

The live planning flow uses the B4.run server's model key. The automated browser check only proves V2 transport selection.

## Approve memory candidates

When the coordinator calls `remember()`, B4.run stores a durable-memory candidate. The runtime exposes candidates over HTTP:

```text
GET  /memory/candidates
POST /memory/candidates/:id/approve
POST /memory/candidates/:id/reject
```

The browser cannot call those routes directly unless the server sets [`server.cors`](/docs/configuration#server). Without it, the B4.run dev server sends no CORS headers, so the example reaches them through a same-origin catch-all, `app/api/b4/[...path]/route.ts`.

That proxy is **allowlisted**. `app/lib/proxy-allowlist.ts` is a pure function listing the exact method and path shape of every route the browser may reach: the three memory routes above and nothing else. Thread history isn't proxied: the runtime route's runner reads it server to server. Anything else is rejected with 403 and never forwarded. That keeps `POST /threads/:id/resume` and the rest of the agent surface out of reach in a template every B4.run developer copies.

<Callout title="Allowlist before you extend">
  Running, resuming, and cancelling a thread are left off the list on purpose.
  Those go through CopilotKit's own runtime route. Add a route to the allowlist
  only when the browser really needs it, and prefer reads. Note, the proxy
  forwards with no authentication and the example installs no `threadAccess`
  policy. The allowlist limits which routes are reachable, not who can reach
  them, so anything that can reach the Next app and holds a thread id can
  restore that thread through the runtime route unless the runner's `fetch`
  carries a per-request caller. Add a `threadAccess` policy on the B4.run side
  before this leaves your own machine.
</Callout>

`app/components/MemoryPanel.tsx` renders the candidates in Memory mode, which replaces the map column, with Approve and Delete on each. The sidenav's Memory item opens it and shows how many are waiting. Delete maps to `/reject`, which is a hard delete on the server. The panel loads on mount and again at the end of every run. `remember()` lands mid-run, so a memory proposed in the answer you are reading should be reviewable without a reload:

```tsx title="examples/navlog/web/app/components/MemoryPanel.tsx"
useEffect(() => {
  const controller = new AbortController()
  void load(controller.signal)
  return () => {
    controller.abort()
  }
}, [load])

useEffect(() => {
  const subscription = agent.subscribe({
    onRunFinishedEvent: () => {
      void load()
    },
  })
  return () => {
    subscription.unsubscribe()
  }
}, [agent, load])
```

The panel only reviews candidates. It lists every candidate waiting. Browsing, searching, and editing stored memories is still the job of the [`b4 memory`](/docs/memory/long-term) CLI.

<Callout title="Deep runs need a higher recursion limit">
  The coordinator plans, dispatches subagents, and makes many tool calls. The
  navlog route sets `recursionLimit: 100` so a full run can exceed LangGraph's
  default step ceiling.
</Callout>
