# Tools

Tools are the units of work a route's entry can invoke. They live in a route's `tools/` directory (or the shared `src/tools/`), and B4.run discovers them automatically. B4.run **infers their input and output types from TypeScript source**, so tools don't need Zod schemas. (Route state in `state.ts` does use Zod. See [State](/docs/state).)

## A minimal tool

Here is a tool that greets a tenant:

```ts title="src/app/(public)/hello/[tenant]/tools/greet.ts"
export default async (input: { readonly tenant: string }) => {
  return { greeting: `Hello, ${input.tenant}!` }
}
```

That's it. B4.run extracts the input and output types at build time with the TypeScript compiler API and writes them into `.b4/b4.generated.d.ts`. The tool is available as `ctx.tools.greet` inside a `workflow`, or a callable `graph` function that receives B4.run's `RuntimeContext`. `b4 build` wires it into generated `agent` deployment entries. A precompiled raw LangGraph object works differently (see [Invoking a tool](#invoking-a-tool)).

<Callout type="info" title="No registration needed">
  Every `.ts` file in a route's `tools/` directory is automatically discovered. Add a file, save, and the type appears in `ctx.tools` on the next `b4 typegen` or `b4 dev` reload.
</Callout>

## Shared tools

Tools resolve from two locations. Each route gets its own `tools/` directory for tools that belong to that route, and there's a shared `src/tools/` directory for tools reused across routes:

```text
src/
├── tools/                  ← shared across every route
│   ├── lookupOrder.ts
│   └── escalate.ts
└── app/
    └── support/
        ├── index.ts
        └── tools/          ← route-local to /support
            └── escalate.ts
```

Both sets are merged for agent-route materialization and for the typed `ctx.tools` given to workflow or callable-graph functions. When the same tool name exists in both, **the route-local tool shadows the shared one**. In the tree above, `/support` sees its own `escalate` and the shared `lookupOrder`. Put a tool in `src/tools/` when more than one route needs it. Keep it in the route's `tools/` when it's specific to that route or overrides a shared one.

Here is how discovery works for top-level agents and subagents:

| Tool source | Top-level agent route | Subagent route |
|---|---|---|
| Shared authored `src/tools/*` | Available by default | Available by default |
| The route's own local `tools/*` | Available by default | Available by default |
| A parent route's local `tools/*` | Not applicable | Not inherited |
| Active capability tools | Available by default | Withheld unless named in `tools.allow` |

## Scoping a route's tools

By default a top route's agent sees every public tool available to it: its own `tools/*.ts`, the shared `src/tools/`, and capability tools such as `writeFile`, `runBash`, `writeTodos`, `readSkill`, and `remember`/`recall`. You can narrow that set per route by passing `tools: { allow, deny }` to `agent()`:

- **`deny`** revokes a tool, so it is never offered to the model.
- **`allow`** grants a withheld capability tool back into the set.
- **`deny` wins** when a name appears in both.
- Omitting `tools` entirely keeps the route's default set shown above.

```ts title="src/app/research/index.ts"
// src/app/research/index.ts: top route, everything except shell
export default agent({ model: "gpt-5", systemPrompt: "…", tools: { deny: ["runBash"] } })
```

B4.run enforces scope at composition time. A withheld tool is never wired into the generated entry, so the model cannot call it. `b4 check` validates the names you reference, and an unknown tool name (absent from the route's available set) is a build-time error.

### Subagents and capability tools

A subagent keeps its authored tools: shared `src/tools/*` plus its own route-local `tools/*.ts`. It does not inherit the parent route's local tools. Capability tools such as `writeFile`, `runBash`, `writeTodos`, and `remember`/`recall` are withheld unless you name them in `allow`.

Shared authored tools reach children by default, so deny any sensitive one a child should not receive:

```ts title="src/app/research/subagents/researcher/index.ts"
// deployProd is authored in src/tools/, so deny it explicitly for this child.
export default agent({
  model: "gpt-5-mini",
  systemPrompt: "…",
  tools: { allow: ["readFile"], deny: ["deployProd"] },
})
```

### The internal task mechanism

`task` is the model-facing mechanism B4.run contributes when a route has at least one dispatchable child. It is internal and is not part of public tool scoping. A nested subagent with its own dispatchable child receives `task` independently, without adding it to `tools.allow`.

Do not reference `task` in `tools.allow`, `tools.deny`, `tools.approve`, or `tools.constrain`. Every form is invalid and reports `B4_E1004` during `b4 check` and route preparation. Parent-owned [`delegation`](/docs/subagents#delegation-policy) is the sole policy boundary for dispatch.

<Callout type="warn" title="This scopes the surface, not execution">
  Tool scoping controls which tools the model can *call*. It does not constrain what an allowed tool may *do* once invoked. A granted `writeFile` can still write anywhere its implementation permits. For that, see the [execution sandbox](/docs/sandbox).
</Callout>

### Requiring approval per call

`approve` is the third `tools` knob. Any tool named in `approve` (an authored route tool or a capability tool) requires a human-in-the-loop prompt before each call:

```ts title="src/app/ops/index.ts"
export default agent({
  model: "gpt-5",
  systemPrompt: "…",
  tools: { deny: ["runBash"], approve: ["deployProd", "sendEmail"] },
})
```

The prompt shows the call's arguments (a display-only JSON preview), but the decision itself is name-level:

- **Once**: this call runs, and the next call to the same tool prompts again.
- **Always**: adds the exact tool name to the configured permissions store, so future calls proceed without prompting. The default Node store is `.b4/permissions.json`. Custom stores, including Postgres, may persist it elsewhere.
- **Deny**: the call is blocked, and the model receives the denial reason as the tool result.

See [Permissions](/docs/permissions#per-tool-approval) for the full interrupt payload and resume flow.

<Callout type="info" title="Don't list workspace tools in approve">
  `runBash`, `readFile`, `writeFile`, and `listDir` already have their own pattern-aware allow/deny gates (see [Permissions](/docs/permissions)). Adding them to `approve` would double-prompt, and `b4 check` warns if you do.
</Callout>

### Constraining arguments

`constrain` is the fourth scoping knob: a predicate per tool, run at call time against the model's arguments. It returns `true` (allow), a string (deny, returned to the model as the tool result), or `{ approve: true }` (escalate to the [approval prompt](/docs/permissions#per-tool-approval)):

```ts title="src/app/ops/index.ts"
export default agent({
  model: "gpt-5",
  systemPrompt: "…",
  tools: {
    constrain: {
      deployProd: (args, ctx) => {
        const { env } = args as { env?: string }             // args is typed `unknown`
        if (env === "prod") return { approve: true }         // human-in-the-loop
        if (env === "staging") return true                   // allow
        return `Unknown environment "${env}".`               // deny, model sees this
      },
    },
  },
})
```

The predicate receives the parsed `args` and a read-only `ctx` (`{ toolName, routeId, threadId?, signal, params? }`), and it may be async. A predicate that throws, or returns anything other than the three shapes above, **fails closed** (the call is denied). `b4 check` validates only the tool names, not predicate bodies. Don't list a tool in both `approve` and `constrain`. `constrain` wins (it can escalate via `{ approve }`) and `b4 check` warns.

## The runtime signature

The full runtime signature accepted by tool discovery is `(input, ctx) => ...`, where `ctx` is `B4ToolContext` from `@b4run/sdk`. It carries `signal`, `threadId?`, `middleware?` and `fs`:

```ts title="src/app/(public)/hello/[tenant]/tools/greet.ts"
import type { B4ToolContext } from "@b4run/sdk"

export default async (
  input: { readonly tenant: string },
  ctx: B4ToolContext,
) => {
  // Cooperate with cancellation. The AbortSignal is always present.
  const res = await fetch(`https://example.com/hello?tenant=${input.tenant}`, {
    signal: ctx.signal,
  })
  // ctx.middleware is the readonly bag populated by allow({ ... }) in src/middleware.ts.
  // ctx.fs is a sandboxed WorkspaceFs handle for reading and writing workspace files.
  const notes = await ctx.fs.readFile("notes.txt").catch(() => "")
  return { greeting: await res.text(), notes }
}
```

The second parameter is optional. I recommend it for any tool that does network I/O, runs long, needs middleware-derived context, or reads or writes workspace files. See [Middleware](/docs/middleware) for how `defineMiddleware` and `allow(context)` populate `ctx.middleware`, and [Workspace Filesystem](/docs/workspace) for `ctx.fs`.

`ctx.threadId` is the readonly conversation identity the runtime supplies when available. It is separate from model-supplied tool arguments and may be absent outside a threaded invocation, so tools that need it should handle that case. A thread ID is not an authenticated user, an authorization decision or a globally scoped sandbox resource name. Keep your application's access checks and provider isolation policy.

## Tool descriptions

The description the LLM sees for an `agent`-route tool comes from a JSDoc comment directly above the default export:

```ts title="src/app/(public)/hello/[tenant]/tools/greet.ts"
/** Greet the tenant organization by name. */
export default async (input: { readonly tenant: string }) => {
  return { greeting: `Hello, ${input.tenant}!` }
}
```

`b4 typegen` extracts the comment into the route's `tools.json` manifest. To set it programmatically, export a `description` string constant. It takes priority over the JSDoc comment:

```ts title="src/app/(public)/hello/[tenant]/tools/greet.ts"
export const description = "Greet the tenant organization by name."

export default async (input: { readonly tenant: string }) => {
  return { greeting: `Hello, ${input.tenant}!` }
}
```

Tools without a description still work, but the LLM only sees the tool name. I recommend writing the one-liner.

## Invoking a tool

Inside a `workflow`, tools are invoked through `ctx.tools.<name>(...)`:

```ts title="src/app/(public)/hello/[tenant]/index.ts"
// workflow form
import type { RuntimeContext } from "@b4run/sdk"
import type { RouteTools } from "b4:routes"
import state from "./state.js"

export async function workflow(
  input: unknown,
  ctx: RuntimeContext<RouteTools<"/hello/[tenant]">>,
) {
  const parsed = state.parse(input)
  const result = await ctx.tools.greet({ tenant: parsed.tenant })
  return { ...parsed, greeting: result.greeting }
}
```

`ctx.tools.greet` has full IntelliSense for its input and return shapes.

A callable `graph` function may explicitly accept the same B4.run `RuntimeContext` and use `ctx.tools`. A precompiled raw LangGraph object is different: its `.invoke()` treats the second argument as LangGraph `RunnableConfig`, not B4.run's typed `RuntimeContext`. That graph keeps the tools its implementation already owns or imports.

Inside an `agent` route, you do not call tools yourself. `b4 build` wires the route's tools into the generated LangGraph entry, and the LLM invokes them as needed.

## Input and output rules

<Steps>
  <Step title="Use a typed, object-shaped input">
    B4.run's compiler pass extracts serializable input shapes written inline, declared as local aliases or interfaces, or imported from another module. Keep the root input object-shaped so B4.run can emit the model-facing tool schema.

    Imports resolve with your app's own `tsconfig.json` (the nearest one above the app root, including its `extends` chain, `paths`, and `baseUrl`), so an input type that lives behind a path alias such as `@acme/contracts` derives the same schema as a relative import. If a declared input type cannot be resolved (the alias is missing from `tsconfig.json`, or the module has no such export), `b4 typegen` fails and names the tool file and the type. It does not emit a schema with no properties. A tool that genuinely takes no input can omit the parameter or declare it as `{}`.

    ```ts
    export default async (input: { readonly tenant: string; readonly limit?: number }) => { ... }
    ```
  </Step>
  <Step title="Mark fields readonly">
    `readonly` is preserved through type generation. Use it on every field, since tool inputs are pure data.
  </Step>
  <Step title="Keep inputs and outputs JSON-serializable">
    B4.run serializes through the runtime boundary, so classes, Dates, Maps and functions do not survive. Use primitives, plain objects and arrays.
  </Step>
  <Step title="Return serializable data">
    Output types may be inferred or annotated inline, declared as local aliases or interfaces, or imported from another module. Use serializable primitives, arrays and plain objects.
  </Step>
</Steps>

## The generated declarations

`b4 typegen` writes two artifacts:

- **`.b4/b4.generated.d.ts`**: the ambient type module behind `import type { RouteTools } from "b4:routes"`. It holds a `RouteTools<P>` lookup keyed by each discovered route pathname, with concrete tool signatures inferred from source.
- **`.b4/routes/<routeSlug>/tools.json`**: per-route tool-schema manifests that `b4 build` reads when emitting LangGraph entries.

To inspect the exact shape B4.run emits in your app, run `b4 typegen` and open `.b4/b4.generated.d.ts`.

<Callout type="warn" title="Don't edit these files">
  `.b4/b4.generated.d.ts` and the per-route `tools.json` files under `.b4/routes/` are regenerated on every `b4 typegen`, by the dev server on save, and before `b4 run` and `b4 test` execute routes in-process and `b4 build` emits artifacts. Your edits will be wiped.
</Callout>

To regenerate them manually, run:

```
b4 typegen
```

## Common patterns

- **External API wrappers**: one tool per endpoint. The input mirrors the endpoint's parameters, and the output is the parsed response.
- **Database reads**: the input holds the filters, and the output is the records. Keep queries cheap.
- **LLM calls**: the input is the prompt variables, and the output is the parsed model response. Leave orchestration to the route entry.
- **Pure transformations**: shape-to-shape mapping with no side effects. These are easy to test.
- **Wrapping an existing LangChain tool**: instantiate the community tool at module scope, then expose it through a plain function with a typed input. B4.run tools are plain functions (not `tool()` wrappers), so B4.run can infer the types from the signature:

```ts title="src/app/(public)/research/tools/search.ts"
import { TavilySearch } from "@langchain/tavily"

const tavily = new TavilySearch({ maxResults: 5 })

/** Search the web for current information. */
export default async (input: { readonly query: string }) => {
  const results = await tavily.invoke({ query: input.query })
  return { results: String(results) }
}
```

The example wraps the community tool's loosely typed output in a plain object to give it a concrete, serializable return shape. Outputs that are already serializable don't need the wrapper.
