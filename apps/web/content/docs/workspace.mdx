# Workspace Filesystem

The `workspace/` directory at the app root is where a B4.run app keeps its files. Create it, and agent routes get four built-in tools: `listDir`, `readFile`, `writeFile` and `runBash`. There's nothing else to configure. Every file read and write goes through one permission gate, whether the model calls a tool or your code calls `ctx.fs`.

There are three layers:

- **The backend** (`@b4run/workspace`): a plain object that reads, writes and lists files. `localFilesystem()` is the default, and you can swap in your own in `b4.config.ts`.
- **The agent tools**: `readFile`, `writeFile`, `listDir` and `runBash`. B4.run adds them to agent routes when `workspace/` exists at the app root. The model calls them by name, and each call passes the permission gate before it reaches the backend.
- **`ctx.fs`**: the `WorkspaceFs` handle on `B4ToolContext` (route tools) and `RuntimeContext` (workflow and graph entries). It uses the same gate and backend, but your code calls it. It's always on the context. Reads throw `ENOENT` until `workspace/` exists.

## The pluggable backend

Every backend implements the `FilesystemBackend` interface:

| Method | Required | Notes |
|---|---|---|
| `readFile(path, ctx, opts?)` | Yes | UTF-8. `opts.maxBytes` overrides the default cap |
| `realPath(path, ctx)` | Yes | Resolves symlinks so the permission gate sees the real target. Backends without symlinks return the path as-is |
| `readBinaryFile(path, ctx, opts?)` | No | Raw bytes (`Uint8Array`). Needed for `ctx.fs.readBinaryFile` |
| `writeFile(path, content, ctx)` | Yes | Returns `{ bytesWritten }` |
| `listDir(path, ctx)` | Yes | Returns leaf names, not full paths |
| `statFile(path, ctx)` | No | Required for offload GC |
| `removeFile(path, ctx)` | No | Required for offload GC eviction |
| `touchFile(path, ctx)` | No | Used by LRU-by-access offload tracking |
| `mkdir(path, ctx)` | No | Used to create the `tool-outputs/` directory |

`localFilesystem()` implements all of them, with two defaults:

- **A 256 KiB read cap** per call. Override it with `opts.maxBytes` (for example, `Number.POSITIVE_INFINITY` for no cap).
- **`writeFile` creates missing parent directories**, so writing `reports/result.md` works without a `mkdir` first.

To use your own backend, set it in `b4.config.ts`:

```ts title="b4.config.ts"
import { myRemoteBackend } from "./backends/remote.js"

export default {
  backends: {
    filesystem: myRemoteBackend(),
  },
}
```

## Middleware

`FilesystemMiddleware` is `(next: FilesystemBackend) => FilesystemBackend`. Wrap the default backend with `compose()` to add behavior to every call, such as logging:

```ts title="b4.config.ts"
import { compose, withFilesystemLogging } from "@b4run/workspace"
import { localFilesystem } from "@b4run/workspace/node"

export default {
  backends: {
    // compose(...) takes middlewares and returns a wrapper; apply it to the base backend.
    filesystem: compose(withFilesystemLogging())(localFilesystem()),
  },
}
```

`withFilesystemLogging` writes each method name and its arguments to `stderr`. For `writeFile`, that includes the whole file content, so be careful where those logs go. Pass a `destination` function for structured output:

```ts
withFilesystemLogging({
  destination: ({ method, args }) => {
    structuredLogger.debug("workspace", { method, args })
  },
})
```

`readBinaryFile` logs the **path only**, never the bytes.

<Callout type="warn" title="Forward optional methods">
  A middleware that returns only `{ readFile, writeFile, listDir }` silently drops `readBinaryFile`, `statFile`, `removeFile`, `touchFile`, and `mkdir`. Without `statFile` and `removeFile`, offload GC stops working. Without `readBinaryFile`, so does `ctx.fs.readBinaryFile`. Use a conditional spread to pass through the methods you don't intercept:

  ```ts
  return (next: FilesystemBackend) => ({
    readFile: async (path, ctx, opts) => {
      // ... your logic
      return next.readFile(path, ctx, opts)
    },
    writeFile: (path, content, ctx) => next.writeFile(path, content, ctx),
    listDir: (path, ctx) => next.listDir(path, ctx),
    ...(next.readBinaryFile && { readBinaryFile: (p, c, o) => next.readBinaryFile!(p, c, o) }),
    ...(next.statFile && { statFile: (p, c) => next.statFile!(p, c) }),
    ...(next.removeFile && { removeFile: (p, c) => next.removeFile!(p, c) }),
    ...(next.touchFile && { touchFile: (p, c) => next.touchFile!(p, c) }),
    ...(next.mkdir && { mkdir: (p, c) => next.mkdir!(p, c) }),
  })
  ```

  `withFilesystemLogging` does this correctly, so it's a good reference.
</Callout>

## The four agent-facing tools

All paths are relative to `workspace/`. A path outside it goes through the permission gate (see [Permissions](#permissions) below).

### listDir

Lists the file and folder names in a workspace directory. It returns names, without the directory path.

```
listDir({ path: "corpus" })
// → ["intro.md", "api-reference.md", "changelog.md"]
```

Leave out `path` to list the workspace root.

### readFile

Reads a UTF-8 file. The default cap is **256 KiB**. A larger file returns an error, with no partial content.

```
readFile({ path: "corpus/intro.md" })
```

Files in `workspace/tool-outputs/` (where offloaded tool results go) have no size limit, so the agent can read them back in full with the same `readFile` call.

### writeFile

Writes a UTF-8 file. **It creates missing parent directories**, so `writeFile({ path: "reports/2024-q1.md", content: "..." })` works before `reports/` exists.

```
writeFile({ path: "reports/summary.md", content: "# Summary\n\n..." })
// returns: "wrote 1234 bytes to reports/summary.md"
```

### runBash

Runs a shell command in the workspace root. A command runs only if it matches an allow rule or a person approves it (see [Permissions](/docs/permissions)).

```
runBash({ command: "node scripts/fetch-source.mjs https://example.com/api" })
```

## ctx.fs for tools and routes

`ctx.fs` is a `WorkspaceFs` handle. It's a smaller, workspace-relative view of the backend:

```ts
interface WorkspaceFs {
  readFile(path: string, opts?: { readonly maxBytes?: number }): Promise<string>
  readBinaryFile(path: string, opts?: { readonly maxBytes?: number }): Promise<Uint8Array>
  writeFile(path: string, content: string): Promise<{ readonly bytesWritten: number }>
  listDir(path?: string): Promise<readonly string[]>
}
```

Paths are **relative to the workspace**, so `"images/logo.png"` means `<appRoot>/workspace/images/logo.png`. Anything outside the workspace root goes through the permission gate (see [Permissions](#permissions) below).

Here is a route tool that reads a binary file:

```ts title="src/app/(public)/describe/tools/describeImage.ts"
import type { B4ToolContext } from "@b4run/sdk"

export const description = "Describe an image stored in the workspace."

export default async (
  input: { readonly path: string },
  ctx: B4ToolContext,
) => {
  const bytes = await ctx.fs.readBinaryFile(input.path)
  const dataUrl = `data:image/png;base64,${Buffer.from(bytes).toString("base64")}`
  // Pass dataUrl to a vision model call, return the description, etc.
  return { dataUrl }
}
```

`Buffer.from(bytes).toString("base64")` turns the `Uint8Array` into a base64 string. If your backend has no `readBinaryFile`, the call throws an error that tells you how to fix it.

And here's a workflow that lists and reads files. A workflow gets the caller's input as-is, so it parses it first:

```ts title="src/app/(public)/report/index.ts"
import type { RuntimeContext } from "@b4run/sdk"
import type { RouteTools } from "b4:routes"
import { z } from "zod"

const Input = z.object({ topic: z.string() })

export async function workflow(input: unknown, ctx: RuntimeContext<RouteTools<"/report">>) {
  const { topic } = Input.parse(input)
  const entries = await ctx.fs.listDir("drafts")
  const first = entries[0]
  if (!first) return { topic, summary: "no drafts found" }
  const content = await ctx.fs.readFile(`drafts/${first}`)
  return { topic, summary: content.slice(0, 500) }
}
```

`listDir()` with no argument lists the workspace root. Both `readFile` and `listDir` pass the permission gate before they reach the backend.

## Research scaffold example

The `research` template (`create-b4-app --template research`) shows how these tools fit together. These paths are relative to the B4.run app root, which is the generated project's `server/` package:

```text
workspace/
  AGENTS.md          ← agent memory (see /docs/memory)
  corpus/            ← source documents the agent reads
  scripts/
    fetch-source.mjs ← network fetch script called via runBash
  reports/           ← agent-written output (writeFile creates this)
```

Here's how the agent uses them:

- `listDir` and `readFile` explore and read the corpus.
- `runBash` runs `scripts/fetch-source.mjs` when the agent needs a new source. That command is left off the `allow` list on purpose, so a person approves each fetch.
- `writeFile` saves reports to `workspace/reports/`, creating the directory on the first write.

Agent memory lives in `workspace/AGENTS.md`, and B4.run adds it to the system prompt. See [Memory](/docs/memory).

<Callout type="warn" title="Treat AGENTS.md as shared prompt input">
  B4.run reads the app root's `workspace/AGENTS.md` into the prompt on every turn, for every `agent()` route and subagent. With the default local filesystem, `writeFile({ path: "AGENTS.md", ... })` writes that same file. So one route can save instructions that change later requests and every other agent in the app root.

  A sandbox or custom backend may send `writeFile` to a different filesystem, and then the host file stays the same. Raw graph, workflow, and chain routes never read this file.

  Give each tenant its own app root (or its own prompt-memory trust domain). A per-thread sandbox won't separate them, because every thread reads the same host file. Limit or deny writes from untrusted agents that can reach it, review the seeded content, and never copy raw untrusted text into `workspace/AGENTS.md`.
</Callout>

## Tool-output offloading

When a tool returns a large result, B4.run can save it to `workspace/tool-outputs/` and put a short stub in the context. The agent reads the full result back with `readFile` when it needs it. See [Context Management](/docs/context-management) for the options and how offloading works with summarization.

## Permissions

Every file read and write goes through the same permission gate, whether the model calls a workspace tool or your code calls `ctx.fs`:

| Path | Decision |
|---|---|
| Inside `workspace/` | Always allowed silently |
| Outside `workspace/`, allow rule matches | Allowed |
| Outside `workspace/`, deny rule matches | Denied |
| Outside `workspace/`, no rule (unknown), interactive mode, agent-route tool | Interactive prompt shown. A `kind: "path"` interrupt pauses the run for human approval |
| Outside `workspace/`, no rule (unknown), non-interactive mode | Fail-closed |
| Outside `workspace/`, no rule (unknown), workflow/graph entry | Fail-closed with guidance |
| `bypass` mode | Everything allowed (dev only) |

**Non-interactive runs and workflow/graph entries fail closed.** Workflow and graph entries run outside the LangGraph agent graph, so they can't pause for a prompt. When a path outside `workspace/` has no matching rule, the gate returns an error that tells you to add an allow rule:

```
Permission denied: /etc/hosts is outside the workspace and interactive
permission prompts are not available in this execution context.
Add an allow rule for "readFile" to the permissions config in b4.config.ts.
```

**Allow rules match real paths.** The gate compares paths after resolving symlinks, so write allow rules with the **canonical** path. If the workspace or target sits under a symlink (like macOS `/var → /private/var`, or a symlinked home or project directory), a rule written with the symlinked path won't match, and the call fails closed.

**Symlinks resolve before the gate decides.** `localFilesystem` resolves them with `realPath`. A symlink inside `workspace/` that points outside is treated like any outside path: prompted or denied in interactive mode, and denied otherwise. Custom backends get the same protection through `realPath`, which the type requires.

<Callout type="warn" title="Interrupt-resume and side effects">
  When a tool calls `ctx.fs` with an outside path that needs approval, LangGraph pauses in the middle of the tool. On resume, LangGraph **runs the tool again from the top**, so anything before the `ctx.fs` call runs twice.

  Make those side effects safe to repeat, or move them after the gated call.
</Callout>
