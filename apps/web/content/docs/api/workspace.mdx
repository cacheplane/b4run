# @b4run/workspace

## Use this when

Use this package to implement or wrap filesystem, command, and execution-sandbox backends for a B4.run application. The root has the portable backend and sandbox contracts, middleware composition, and logging wrappers. Import `/node` for local filesystem/shell implementations and immutable source capture utilities.

## Install and import

```bash
npm install @b4run/workspace
```

```ts
import { compose, withExecLogging, type SandboxProvider } from "@b4run/workspace"
import { localExec, localFilesystem } from "@b4run/workspace/node"
```

| Surface | Runtime | Purity | Audience | Stability |

## Key contracts

### Bounded text inspection

`inspectWorkspace(source, options?)` accepts a `WorkspaceFs` or `SandboxHandle`.
It returns `{ files, symlinks, totalBytes, entries }`. File keys are relative paths.
Metadata and binary reads are required. Unsupported entries, executable files,
NUL bytes, invalid UTF-8, and exceeded limits fail inspection. UTF-8 BOMs remain
part of the returned text.

Defaults are 10,000 entries, 2 MiB per file, and 16 MiB total. Override these with
`maxEntries`, `maxFileBytes`, and `maxTotalBytes`. `excludeRootDirectories` omits
only directory subtrees. A file or link at an excluded name fails. Every entry in
`expectedRootSymlinks` must exist with its exact raw link target. Other symlinks
are rejected. `signal` cancels inspection.

```ts
import { inspectWorkspace } from "@b4run/workspace"

const inspection = await inspectWorkspace(ctx.fs, {
  signal: ctx.signal,
  maxTotalBytes: 2 * 1024 * 1024,
  excludeRootDirectories: [".git"],
})
```

When a backend implements both `walkTree` and `readBinaryFiles`, inspection
walks the tree in one call and reads the files in as few calls as the backend
allows. The Docker and Kubernetes backends implement both, so inspecting a
container workspace costs a few execs instead of one per entry. The checks and limits
are the same either way. A batched inspection also refuses a file that grew
between the walk and the read.

Inspection uses separate metadata and read operations, so it is not an atomic
snapshot. Quiesce writers or revalidate before acting on an inventory. Expected
links establish link identity, not the contents of their targets. Custom backends
must honor byte limits during reads to bound allocation. The built-in local,
Docker, and Kubernetes readers cap content before collecting it.

`openWorkspaceReader` is an optional capability. Presence is the probe: a provider whose storage cannot be attached a second time omits it rather than implementing it unreliably. An implementation must leave the thread's sandbox undisturbed, make writes impossible rather than merely undocumented, and reject rather than return an empty view when the thread has no workspace storage.

It is not an authorization boundary. The caller already holds the provider. Naming a thread id is not a claim of ownership.

```ts api-contract="@b4run/workspace#./node:captureWorkspaceSource"
export declare function captureWorkspaceSource(
  appRoot: string,
  definition: WorkspaceSourceDefinition,
  options?: { readonly signal?: AbortSignal },
): Promise<SourceBundle>
```

`createSourceBundle` copies explicit bytes into sorted, frozen file entries and
computes a versioned SHA256 identity covering paths, content, and executable bits.
`verifySourceBundle` rejects malformed or noncanonical entries and digest mismatch;
it returns a new frozen bundle. `readSourceFile` verifies the bundle, rejects a
missing path, and returns an independently owned byte array.

`captureWorkspaceSource` resolves directory and referenced file paths relative to
`appRoot`. `directory: "."` selects that root. `include` is an exact inventory of
regular files relative to the source directory. Missing or extra files fail.
`excludeDirectories` names existing directory subtrees to skip, without following
symlinks. Additional `files` entries declare destination paths with either a file
reference relative to `appRoot`, or inline text and an optional executable flag.
Text preserves BOMs and rejects malformed Unicode. Referenced files preserve their
executable flags. Duplicate destinations, conflicting ancestors, and inconsistent
directory casing are rejected.

Bundles allow at most 10,000 files, 16 MiB per file, and 64 MiB total content.
Capture also limits distinct inspected filesystem paths to 10,000,
including the app root, ancestor directories, exclusions, and extra references.
Paths use an ASCII portability subset, at most 1,024 bytes per path and 255 bytes
per segment. Traversal, absolute paths, backslashes, device names, leading/trailing
spaces, consecutive spaces, trailing dots, and case-insensitive collisions fail.
Leading dotfiles such as `.gitignore` are supported.

Capture rejects symlinks and special files, checks size before allocating file
buffers, and detects changes through file metadata and inventory rechecks. It
reads a trusted application tree: these checks are not an atomic snapshot or a
defense against a hostile host process swapping ancestor directories. Cancellation
closes open handles and returns no completed bundle. These utilities do not create
sandboxes or activate managed workspace recovery in runtime configuration.

### Lifecycle, failures, and trust

Backend methods receive absolute paths and a cancellation signal from their caller. Core owns the path jail and canonical-root enforcement. `localFilesystem` canonicalizes existing ancestors, including escaping symlinks, and does not enforce that boundary. Its reads default to a 256 KiB cap, allow a per-call override, and reject missing or oversized files. Writes create parent directories.

`localExec` defaults to a 30-second timeout. A non-empty `allowedCommands` list rejects a command unless a regular expression matches. When `args.env` is omitted, `localExec` inherits `process.env`. When supplied, it replaces that environment. By contrast, `SandboxPolicy.env` is the explicit environment injected into a sandbox and does not inherit the host environment.

Sandbox `release()` and `destroy()` have distinct lifecycle roles. Each provider defines the exact persistence and cleanup behavior. Security fields express provider-agnostic intent. An unset field does not by itself prove a particular provider's enforcement.

Logging middleware defaults to `console.error`. A custom destination receives `{ method, args }`. Filesystem logging does not serialize binary content and passes through `realPath`, `statFile`, `removeFile`, `touchFile`, and `mkdir`. Treat logged paths, command text, working directories, and text write contents as potentially sensitive.

### Managed workspace lifecycle

Declare `sandbox.workspace` with an exact source inventory. `b4 build` captures
source bytes for the Node target. Startup verifies the artifact and retains it
in the installation store. Existing threads retain their original source and
provenance across deployment changes. Providers without `workspaces` support
reject the configuration. The first qualified provider is Docker. Managed
workspace builds require `build: { targets: ["node"] }` and the existing app-root
`workspace/` capability marker.

`sandbox.workspace` may instead be a `WorkspaceResolver`: host code called once per
thread, at the thread's first admission, with the thread id and its stored client
metadata. B4.run captures what it returns (or verifies it, if already captured) and
records it by digest in that thread's creation intent. It's never re-resolved. Later
turns, restarts and readers all use the record.

`b4 build` can't capture a resolver, so the artifact only records that one is
configured, and startup refuses an artifact whose form disagrees with the loaded
config. Deployed host code decides the result, never the client or the model. A
resolver treats the metadata it is given as input to validate, not as authority.

The resolver sees the thread's stored metadata with B4.run's reserved
key stripped. On the server run endpoints (`runs/stream`, `runs/wait`, AG-UI), `route` is
present and server-authoritative, because the runtime stamps it before admission and the
store's merge overwrites any client value. Under `b4 run` it is absent. Every other key is
client-writable, so never use metadata as an authorization input.

`POST /threads` always assigns the id, so to attach metadata before the first
resolution, create the thread and use the id it returns. `b4 run` creates a fresh
thread per invocation, so the resolver runs on every run with empty metadata.

Provider creation receives an immutable `SourceBundle`, bounded to 64 MiB of
original content, and a persisted `WorkspaceCreateIntent`. Readiness must match
that intent before tools receive a session. An unknown outcome cannot authorize
a new operation. Release targets a compute incarnation. Destroy targets the
original operation and may run before readiness exists. Missing established
storage is an explicit failure, never an instruction to reseed.

Environment links point to directories in the pinned immutable environment.
They cannot overlap source files or generated `.git` metadata. Docker requires
a Node-capable preparation image, keeps those targets read-only, and supports
UID/GID 1000 for managed non-root execution. Git baselines use fixed identity
and time with ambient configuration and hooks disabled. The stored baseline
commit is provenance. Agent-writable `.git` contents are not verification truth.

`sandbox.thread` goes one step further: a `ThreadSandboxResolver` returns the thread's
workspace, an optional image and optional policy overrides, once, at first admission.
Every thread admitted this way has a record, and a thread-mode admission of a thread
without one is refused as a conflict.
The provider's `resolveImageEnvironment` turns the image into the identity recorded in
the creation intent, and B4.run writes the image reference and the policy to a
per-thread record in the same transaction as the association. Every reconnect runs the
thread's recorded policy over the app's; nothing is re-resolved. A provider without
`resolveImageEnvironment` refuses a thread that names an image.
