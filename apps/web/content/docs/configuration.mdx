# Configuration Reference

`b4.config.ts` configures your B4.run app. Every `B4Config` field is optional,
but the file is required, because the CLI finds your app by looking for it
next to `package.json`. Node loads it once, and `b4 dev` restarts its child
runtime when you edit it. Filesystem-free runtimes receive a config object
and never read the file.

Run [`b4 verify`](/docs/cli) before you serve the app. It checks the config,
routes, Node version, provider credentials and sandbox preflight.

## Complete annotated example

You can copy this file as written. Uncomment an instance-valued field once
you've imported or built its implementation:

```ts title="b4.config.ts"
import { config } from "@b4run/cli"

export default config({
  appDir: "src/app",

  // A configured sandbox overrides these backends for sandboxed threads.
  backends: {
    // filesystem: customFilesystem,
    // exec: customExec,
  },

  permissions: {
    mode: "interactive",
    allow: { bash: ["ls", "cat"], tool: ["deployPreview"] },
    deny: { bash: ["rm -rf"] },
    // store: sharedPermissionsStore,
  },

  // Defaults are local SQLite/file stores under .b4/.
  // checkpointer: sharedCheckpointer,
  // threadsStore: sharedThreadsStore,

  // Used by b4 dev/inspect; b4 start receives env from its host.
  env: "./.env",

  toolOutput: {
    offloadThresholdChars: 40_000,
    previewLines: 10,
    maxBytes: 268_435_456,
    ttlMs: 10_800_000,
    gcThrottleMs: 10_000,
    noOffloadTools: [],
  },

  summarization: {
    enabled: false,
    maxTokens: 12_000,
    keepRecentTurns: 6,
    // model: "gpt-5-mini",
    // tokenCounter: async (text) => countTokens(text),
    // summarize: async ({ messages, model, previousSummary, signal }) => "...",
  },

  build: {
    targets: ["node", "langsmith"],
    // vercel: { outDir: "dist/vercel" }, // where the "vercel" target publishes (default .vercel/output)
  },

  // Cross-origin access. Omit it and the runtime sends no `Access-Control-*`
  // header, so a browser on another origin cannot call it.
  // `localhost` and `127.0.0.1` are different origins to a browser.
  server: {
    cors: { origins: ["https://app.example.com"] },
  },

  // sandbox: {
  //   provider: dockerSandbox({ scope: "my-app", image: "node:24-slim" }),
  //   network: { mode: "deny" },
  //   // network: { mode: "deny", allowlist: ["10.0.0.0/8"] }, // Kubernetes CIDRs; Docker ignores it
  //   // network: { mode: "allow" }, // open egress, cloud metadata endpoint included
  //   env: { NODE_ENV: "production" },
  //   resources: { memoryMb: 1024, cpus: 1, timeoutMs: 120_000, diskGb: 10 },
  //   security: {
  //     dropAllCapabilities: true,
  //     noNewPrivileges: true,
  //     readOnlyRootFilesystem: true,
  //     runAsNonRoot: true,
  //     // runAsNonRoot: { uid: 1000, gid: 1000 },
  //     pidsLimit: 512,
  //   },
  //   idleTimeoutMs: 600_000,
  // },

  memory: {
    // enabled: true, // inert compatibility field; memory.ts opts a route in
    // store: sharedMemoryStore,
    writes: "candidate",
    indexMaxEntries: 20,
    recall: {
      weights: { relevance: 0.6, recency: 0.3, confidence: 0.1 },
      recencyHalfLifeMs: 1_209_600_000,
      candidatePool: 256,
    },
    // vector: {
    //   embedder,
    //   weights: { keyword: 1, vector: 1 },
    //   rrfK: 60,
    //   vectorK: 64,
    //   recencyWeight: 0.3,
    //   confidenceWeight: 0.1,
    // },
    episodes: {
      enabled: false,
      ttlMs: 2_592_000_000,
      cap: 500,
      includeFailedRuns: true,
      embed: false,
    },
    distill: {
      model: "gpt-5-mini",
      provider: "openai",
      maxBatches: 5,
      consolidate: {
        olderThanMs: 604_800_000,
        minBatchSize: 5,
        maxBatchSize: 50,
        // ttlMs: 2_592_000_000,
        sourceTtlMs: 604_800_000,
      },
      reflect: { minNewRecords: 10, maxRecords: 100, writes: "candidate" },
    },
    // resolveScope: ({ routePath, appRoot }) => ({ route: routePath, app: appRoot }),
  },
})
```

## Key reference

### `appDir`

```ts
appDir?: string
```

Default: `"src/app"`. This is the directory, relative to the app root, where
B4.run looks for route `index.ts` files. Keep it inside the app root. There's
no environment variable override. See [Routes](/docs/routes) for the layout.

### `backends`

```ts
backends?: {
  filesystem?: FilesystemBackend
  exec?: ExecBackend
}
```

Defaults: the local filesystem and a local child-process executor. A sandboxed
thread uses the sandbox's filesystem and executor. Every other thread uses the
backends you configure here, or the local defaults. Live backend objects can't
be serialized into a static edge build. See [Workspace
Filesystem](/docs/workspace) for backend composition and the path jail.

### `permissions`

```ts
permissions?: {
  mode?: "interactive" | "non-interactive" | "bypass"
  allow?: Readonly<Record<string, readonly string[]>>
  deny?: Readonly<Record<string, readonly string[]>>
  store?: PermissionsStore
}
```

Without a custom store, the defaults are `mode: "interactive"`, empty `allow`
and `deny` maps, and `.b4/permissions.json` for saved interactive decisions.
`B4_PERMISSIONS_MODE` overrides `permissions.mode`. A deny match beats an
allow match. The reserved `tool` and `subagent` keys use exact matching, while
resource paths, bash commands, and memory scopes use prefix matching.

Config `allow` and `deny` maps stay in memory and do not seed the runtime permissions store.
Only an interactive **Always** decision saves an allow entry. See
[Permissions](/docs/permissions) for the modes and the interrupt/resume
lifecycle.

#### `permissions.store`

A `PermissionsStore` you supply replaces the file-backed store, and B4.run
loads it before first use. Your store decides its own mode and allow/deny
policy, so B4.run ignores the sibling `permissions.mode`, `allow`, `deny` and
`B4_PERMISSIONS_MODE`. In an embedded runtime, a store passed at boot wins over
this field.

### `checkpointer`

```ts
checkpointer?: BaseCheckpointSaver
```

Default: SQLite at `.b4/checkpoints.sqlite`. A checkpointer passed at boot wins,
then this field, then the default. Checkpoints hold graph state. Thread
metadata lives in `threadsStore`. Read [Persistence and
Tenancy](/docs/persistence) before you share or delete state across replicas.

### `threadsStore`

```ts
threadsStore?: ThreadsStore
```

Default: SQLite at `.b4/threads.sqlite`. A thread store passed at boot wins,
then this field, then the default. It holds Agent Protocol thread metadata.
Graph state lives in `checkpointer`, so configure both when replicas share
threads. See [Persistence and Tenancy](/docs/persistence) for what each store
holds and the order to delete in.

### `env`

```ts
env?: string
```

Default: `"./.env"`, relative to the app root. Only `b4 dev` and `b4 inspect`
load it, and they check `--env-file` first, then `config.env`, then the
default. `b4 verify` checks the resolved file without loading it. `b4 start`
ignores this field, so production variables come from the shell or your
hosting platform.

The LangSmith artifact picks its own file: `.env.example` when it exists, and
`.env` otherwise. Its JSON records an env-file path, not variable names, and it
ignores `config.env`. See [Deployment Options](/docs/deployment) for how each
target gets its environment.

### `toolOutput`

```ts
toolOutput?: {
  offloadThresholdChars?: number
  previewLines?: number
  maxBytes?: number
  ttlMs?: number
  gcThrottleMs?: number
  noOffloadTools?: readonly string[]
}
```

On a Node runtime with a workspace filesystem, the defaults are `40_000`
characters, `10` preview lines, `268_435_456` bytes (256 MB), a `10_800_000` ms
(3 hour) TTL, and a `10_000` ms GC throttle. `noOffloadTools` defaults to `[]`,
and `readFile` and `listDir` are always exempt. Each value you set replaces
just that default.

Offloaded data lives under `workspace/tool-outputs/`. It keeps large outputs
out of the context window, and it gets cleaned up. A
non-empty block fails on the filesystem-free Hono target (`B4_E1005`). See
[Context Management](/docs/context-management) for retrieval and cleanup.

### `summarization`

```ts
summarization?: {
  enabled?: boolean
  maxTokens?: number
  keepRecentTurns?: number
  model?: string
  tokenCounter?: (text: string) => number | Promise<number>
  summarize?: (args: {
    messages: readonly unknown[]
    model: string
    previousSummary?: string
    signal: AbortSignal
  }) => Promise<string>
}
```

Defaults: disabled, `maxTokens: 12_000`, `keepRecentTurns: 6`, the route model,
a lazy-loaded `gpt-tokenizer` `o200k_base` counter, and the built-in one-call
summarizer. Each field you set replaces its default. Summarization needs a
model, so set `summarization.model` if the route doesn't have one. See
[Context Management](/docs/context-management) for when history gets
compressed and what's kept word for word.

### `build`

```ts
build?: {
  targets?: readonly BuildTargetName[]
  vercel?: {
    functionName?: string
    maxDuration?: number
    static?: { dir: string; spaFallback?: string }
    functions?: Readonly<Record<string, {
      entry: string
      runtime?: string
      maxDuration?: number
      supportsResponseStreaming?: boolean
    }>>
    routes?: readonly { src: string; dest?: string; [key: string]: unknown }[]
    outDir?: string
    reconcileVercelJson?: boolean
  }
}
```

Default: `["node", "langsmith"]`. A `targets` array you set replaces that list
rather than adding to it. `"hono"` and `"vercel"` are the opt-in edge targets.
Pick only targets whose runtime supports the features you use. See
[Deployment Options](/docs/deployment).

`BuildTargetName` is the union `"node" | "langsmith" | "hono" | "vercel"`. It's
exported from `@b4run/core` along with the `BUILD_TARGET_NAMES` tuple it comes
from, so a misspelled target fails to type-check before you ever run
`b4 build`.

`vercel` describes what the `"vercel"` target publishes next to the runtime
function:

- a static directory, with an optional SPA fallback document,
- extra Node functions, each bundled from an `entry`, and
- routes placed ahead of the filesystem phase.

Paths resolve from the app root. The runtime function is named `b4`, because
the Build Output API serves a function named `index` at `/`, where it would
shadow a static `index.html`. `functionName` overrides the name, and `"index"`
next to `static` fails the build. See
[the `vercel` target](/docs/deployment/edge#the-vercel-target) for the
published tree and route order.

`vercel.maxDuration` is the runtime function's `maxDuration` in seconds, a
positive integer. Leave it out and `.vc-config.json` omits it, so Vercel
applies the project default. The runtime function runs the agent, so a long
tool-using run hits the limit there first. Each function under
`vercel.functions` sets its own. `validateVercelOutput` requires the published
value to match the configured one.

`vercel.outDir` is where the Build Output tree is published, relative to the
app root. It defaults to `.vercel/output`, which is where Vercel deploys from.
Point it elsewhere when a later step composes the tree before deploying.
`b4 build --out-dir <dir>` overrides it for one run. Each build replaces the
directory wholesale, so B4.run rejects an `outDir` that contains the app root.

`vercel.reconcileVercelJson` (default `true`) controls whether the `"vercel"`
target keeps the app-root `vercel.json` in line with what it needs: a
`buildCommand` that runs `b4 build`, and `fluid: true`.

Set it to `false` for a prebuilt flow, where CI runs `vercel deploy --prebuilt`
and there's no Vercel Git integration. Vercel never runs `buildCommand` in that
flow, so the target stops requiring, writing or inspecting a committed
`vercel.json`. Keep fluid compute on in the Vercel project settings, because
the build no longer catches a committed `fluid: false`.

One resolver validates all of `build.vercel`. Both `b4 check` and `b4 build`
fail with `B4_E1003` on any near miss:

- a `vercel` value that isn't an object,
- an unknown key inside it,
- a `reconcileVercelJson` other than `true` or `false`, or
- the flag placed directly on `build`.

A prebuilt app sets
`build: { targets: ["vercel"], vercel: { reconcileVercelJson: false } }`.

### `sandbox`

```ts
sandbox?: {
  workspace?: WorkspaceDefinition
  thread?: ThreadSandboxResolver
  workspaceRead?: "http"
  workspaceReadTimeoutMs?: number
  stagedWorkspaces?:
    | boolean
    | {
        maxUploadBytes?: number
        retentionMs?: number
        maxStagedBytes?: number
        uploadTimeoutMs?: number
      }
  provider: SandboxProvider
  network?:
    | { mode: "allow"; denylist?: readonly string[] }
    | { mode: "deny"; allowlist?: readonly string[] }
  env?: Readonly<Record<string, string>>
  resources?: { memoryMb?: number; cpus?: number; timeoutMs?: number; diskGb?: number }
  security?: {
    dropAllCapabilities?: boolean
    noNewPrivileges?: boolean
    readOnlyRootFilesystem?: boolean
    runAsNonRoot?: boolean | { uid: number; gid: number }
    pidsLimit?: number
  }
  idleTimeoutMs?: number
}
```

Default: no sandbox, so workspace operations run on the host backends. If you
add a sandbox, `provider` is required. The manager then defaults to:

- an allow-mode network policy, `{ mode: "allow" }`, with open egress. The
  reference Docker and Kubernetes providers do not enforce a `denylist`, so the
  cloud metadata endpoint `169.254.169.254` stays reachable. See
  [Network policy](/docs/sandbox#network-policy),
- no host environment variables, and
- releasing idle compute after `600_000` ms.

`thread` decides each thread's workspace, image and policy once, when the thread
is first admitted, and is exclusive with `workspace`. `b4 check`, `b4 build` and
startup refuse any other key in the `sandbox` block. Read [Per-thread
sandboxes](/docs/sandbox#per-thread-sandboxes) for what a thread may set.

`workspaceRead: "http"` serves a read of each thread's managed workspace at
`POST /threads/:thread_id/workspace/inspect`. It needs `workspace` or `thread`
and a thread-access policy; `b4 check`, `b4 build` and startup refuse it
without one. `workspaceReadTimeoutMs` (1,000 to 1,800,000; default 120,000)
bounds one read, open to close. Read [Reading a thread's workspace over
HTTP](/docs/sandbox#reading-a-threads-workspace-over-http).

`stagedWorkspaces` accepts a thread's workspace at creation: a creator uploads
it at `PUT /workspace/sources/:digest` and names it in `POST /threads`, and the
resolver receives it as `thread.staged`. It needs a resolver (`thread`, or a
function `workspace`) and a thread-access policy; `b4 check`, `b4 build` and
startup refuse it otherwise. `maxUploadBytes` (default and ceiling 96 MiB),
`maxStagedBytes` (default 1 GiB, at most 16 GiB), `retentionMs` (60,000 ms
to 30 days; default 24 hours) and `uploadTimeoutMs` (1,000 to 1,800,000 ms;
default 120,000) bound it. Read [Handing a thread its workspace at
creation](/docs/sandbox#handing-a-thread-its-workspace-at-creation).

Each provider enforces resources and security in its own way. Docker's
security fields default to hardened. `diskGb` applies to PVC-backed providers,
and Docker ignores it. At runtime, an
injected `sandboxManager` takes precedence over `config.sandbox`, so this
field only applies when the host doesn't pass a manager. Read [Execution
Sandbox](/docs/sandbox) before you relax isolation or network policy.

### `memory`

```ts
memory?: {
  enabled?: boolean
  store?: MemoryStoreLike
  writes?: "off" | "candidate" | "auto" | "ask"
  indexMaxEntries?: number
  recall?: {
    weights?: { relevance?: number; recency?: number; confidence?: number }
    recencyHalfLifeMs?: number
    candidatePool?: number
  }
  vector?: {
    embedder: Embedder
    weights?: { keyword?: number; vector?: number }
    rrfK?: number
    vectorK?: number
    recencyWeight?: number
    confidenceWeight?: number
  }
  episodes?: {
    enabled?: boolean
    ttlMs?: number
    cap?: number
    includeFailedRuns?: boolean
    embed?: boolean
  }
  distill?: {
    model?: string
    provider?: ModelProviderId
    maxBatches?: number
    consolidate?: {
      olderThanMs?: number
      minBatchSize?: number
      maxBatchSize?: number
      ttlMs?: number
      sourceTtlMs?: number
    }
    reflect?: {
      minNewRecords?: number
      maxRecords?: number
      writes?: "candidate" | "auto"
    }
  }
  resolveScope?: (ctx: { routePath: string; appRoot: string }) => Record<string, string>
}
```

A route opts into typed memory with its own `memory.ts` file. `enabled` is an
inert compatibility field.

The defaults are:

- **Store:** SQLite at `.b4/memory.sqlite`, with `writes: "candidate"` and
  `indexMaxEntries: 20`. At runtime, an injected `memoryStore` takes precedence over `config.memory.store`.
- **Keyword recall:** relevance/recency/confidence weights `0.6`/`0.3`/`0.1`,
  a 14-day half-life, and a `256`-record candidate pool.
- **Vector recall:** off. Turn it on with an `embedder`. It then defaults to
  keyword/vector weights `1`/`1`, `rrfK: 60`, `vectorK: 64`,
  `recencyWeight: 0.3`, and `confidenceWeight: 0.1`.
- **Episodes:** disabled, with a 30-day TTL, a cap of `500`, failed runs
  included, and no embeddings (`embed: true` isn't supported).
- **Distillation:** runs only when you invoke it, with `gpt-5-mini`, the
  inferred provider (falling back to `openai`) and five batches.
  Consolidation takes records older than seven days in batches of 5–50, sets
  no summary TTL, and gives source records a seven-day TTL. Reflection waits
  for 10 new records, reads at most 100, and writes candidates.

A custom store ignores these tuning blocks. `resolveScope` receives only
`routePath` and `appRoot`, so derive tenant or user dimensions from your own
application context.

See [Long-term Memory](/docs/memory/long-term) for write governance, [Recall and
Retrieval](/docs/memory/retrieval) for ranking, [Episodes](/docs/memory/episodes)
for run history, and [Distillation](/docs/memory/distillation) for
consolidation and reflection.

### `server`

```ts
server?: {
  cors?: {
    origins: readonly string[] | "*"
    credentials?: boolean
    methods?: readonly string[]
    headers?: readonly string[]
    exposeHeaders?: readonly string[]
    maxAgeSeconds?: number
  }
}
```

By default there's no `server.cors`, which means **no `Access-Control-*` header
on any response**. A browser on another origin can't call `/agui/*`,
`/threads/*` or `/memory/*`, and `OPTIONS` falls through to the router's 404.
Opening a server to other origins is a deployment decision, so B4.run leaves
it to you.

Set it when a browser talks to B4.run directly, without a same-origin proxy:

```ts
server: { cors: { origins: ["https://app.example.com"] } }
```

B4.run normalizes case and a trailing slash, then compares origins as strings,
so `"HTTP://LocalHost:3010/"` matches an `Origin: http://localhost:3010`. Note,
`localhost` and `127.0.0.1` are *different* origins. List both if you open your
dev client at either one.

B4.run validates the policy at boot, so a malformed origin list fails on
startup. It rejects
`origins: "*"` with `credentials: true`, because browsers refuse a wildcard
allow-origin on a credentialed request.

The other fields default to:

- `credentials`: `false`
- `methods`: `GET, POST, DELETE, OPTIONS`
- `headers`: echoes the browser's own `Access-Control-Request-Headers`, so you
  can add an auth header without changing server config
- `exposeHeaders`: empty
- `maxAgeSeconds`: `600`

A request from an origin that isn't on the list is still served. The response
just has no CORS header, so the browser won't hand it to the page. (A 403
would break every non-browser client that sends an `Origin`.) Error responses
carry the headers too, including the shutdown 503, so a cross-origin caller
sees the real 404 rather than an opaque CORS failure.

CORS controls which origins a browser lets read a response. It's not
authentication, and it doesn't decide who may call the server. Pair it with
[`defineThreadAccess`](/docs/thread-access).


## Postgres backend

Shared Postgres persistence takes three explicit entries: the checkpointer, the
thread store and the permission store. Each holds different data with its own
lifecycle. Install the package and the driver:

```bash
npm install @b4run/postgres-storage pg
```

Then wire all three to one pool:

```ts title="b4.config.ts"
import { config } from "@b4run/cli"
import {
  createPostgresPermissionsStore,
  createPostgresThreadsStore,
  postgresCheckpointer,
} from "@b4run/postgres-storage"
import { Pool } from "pg"

export const pool = new Pool({ connectionString: process.env.DATABASE_URL })
pool.on("error", (error) => {
  console.error("Postgres pool client error:", error)
})

export default config({
  checkpointer: postgresCheckpointer({ pool }),
  threadsStore: createPostgresThreadsStore({ pool }),
  permissions: {
    store: createPostgresPermissionsStore({ pool, mode: "non-interactive" }),
  },
})
```

Always attach an `error` listener to the pool. Your application owns the pool,
so end it yourself once B4.run has stopped accepting and draining requests.
The stores leave it open. Postgres shares durable rows between replicas, but it
does not distribute active-run or cancel coordination between processes. Use
sticky or thread-aware routing, or add your own distributed coordination.

See [Persistence and Tenancy](/docs/persistence) for migrations, lifecycle,
retention and deletion, then [Production
Topology](/docs/production-topology) for replica routing and shutdown order.
