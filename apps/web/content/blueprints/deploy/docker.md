# Containerize your B4.run app with Docker

You are an AI coding agent preparing a B4.run app for self-hosting with the `node` build target. B4.run generates the production server and its hardened Dockerfile. Use those artifacts directly; do not hand-author a competing Dockerfile.

## Prerequisites

Confirm these prerequisites before changing the app:

1. **Node.js 24 or newer** — B4.run packages require Node >=24:

   ```bash
   node --version
   ```

   If the reported major is below 24, switch or upgrade Node before continuing.

2. **Docker** — confirm the daemon tooling is installed:

   ```bash
   docker --version
   ```

   If Docker is unavailable, install it from [docker.com/get-started](https://www.docker.com/get-started/) before building the image.

3. **Project conventions and package metadata** — read `AGENTS.md` when present, then inspect `b4.config.ts`, `package.json`, every lockfile, `.dockerignore`, and any existing root `Dockerfile`. Do not assume the generated image uses the repository's preferred package manager; its install step is always npm.

## Keep the CLI at runtime

The emitted `.b4/build/server.mjs` imports `@b4run/cli` when the container starts. Ensure `package.json` lists `@b4run/cli` under `dependencies`, not only `devDependencies`; the generated image installs production dependencies and strips dev-only packages.

Use the project's package manager to move or add the existing compatible B4.run version, for example:

```bash
pnpm add @b4run/cli
# npm install --save @b4run/cli
# yarn add @b4run/cli
```

Preserve the app's existing version range or workspace specifier when moving the dependency.

## Prepare a current npm lockfile

The generated Dockerfile is not package-manager-aware. It copies `package.json`, an optional `package-lock.json`, and an optional `pnpm-lock.yaml`, then always runs:

```dockerfile
RUN npm ci --omit=dev || npm install --omit=dev
```

It never runs pnpm or Yarn, and a pnpm or Yarn lockfile does not constrain npm's resolver. Require a current `package-lock.json` for a reproducible production image, even when contributors use another package manager locally:

```bash
npm install --package-lock-only --ignore-scripts
npm ci --omit=dev --dry-run
```

Review and commit the resulting lockfile. A pnpm- or Yarn-only repository otherwise gets an npm-resolved dependency graph inside the image, which can differ from local development. If repository policy forbids `package-lock.json`, stop: the current generated Dockerfile cannot provide a lockfile-reproducible install for that repository. Do not hide the mismatch by hand-authoring another Dockerfile in this blueprint.

During `docker build`, confirm `npm ci --omit=dev` succeeds. The generated `|| npm install --omit=dev` fallback is recovery behavior, not a reproducibility guarantee; investigate and fix any lockfile mismatch that triggers it.

## Select the Node target

Merge this target selection into the existing `b4.config.ts` rather than replacing unrelated configuration:

```ts
import { config } from "@b4run/cli"

export default config({
  // Keep the app's existing settings here.
  build: { targets: ["node"] },
})
```

Naming `build.targets` replaces the default target list. `['node']` asks B4.run only for the self-hosted Node runtime artifacts.

## Verify and build

From the app root, run the current verification workflow and regenerate a clean build:

```bash
pnpm exec b4 verify
pnpm exec b4 test
pnpm exec b4 build --clean
```

Use `npx b4 ...` or `yarn b4 ...` equivalents when that is the project's package manager. Fix failures before building an image.

The Node target emits:

- `.b4/build/server.mjs` — the production entry point that boots the B4.run HTTP runtime.
- `.b4/build/modules.mjs` — the static route, tool, state, memory, and middleware module manifest generated from the app.
- A generated Dockerfile containing B4.run's authoritative marker:

  ```text
  # Generated by b4 build (node target). Safe to edit; delete to regenerate.
  ```

Dockerfile placement is marker-aware:

- With no root `Dockerfile`, B4.run writes the generated file at `./Dockerfile`.
- If the root file still contains B4.run's generated marker, the next build refreshes it in place.
- If the root file is user-authored or the marker was removed, B4.run preserves it and writes the generated file to `.b4/build/Dockerfile`.

Do not add the legacy `# b4-blueprint: docker@2` marker or manually recreate the generated contents. B4.run's generated-file marker above is the only marker that controls refresh behavior.

## Keep the build artifact in the Docker context

The generated Dockerfile copies the host-built `.b4/build/` directory into the image; it does not rerun `b4 build` inside the container. Make sure the app root is the Docker build context and that `.dockerignore` does **not** exclude `.b4`, `.b4/build`, `server.mjs`, or `package-lock.json`.

It is safe and recommended to exclude local dependencies, source-control data, and secrets while retaining `.b4/build`:

```text title=".dockerignore"
node_modules
.git
.env
.env.*
coverage
```

Review an existing `.dockerignore` rather than overwriting it. Remove any broader `.b4` rule before building.

## Build the emitted Dockerfile

Use the path B4.run actually emitted. After `b4 build --clean`, this shell snippet selects the marked root file or the preserved-user-file fallback and verifies it exists:

```bash
B4_DOCKERFILE=Dockerfile
if ! grep -Fq '# Generated by b4 build (node target). Safe to edit; delete to regenerate.' "$B4_DOCKERFILE" 2>/dev/null; then
  B4_DOCKERFILE=.b4/build/Dockerfile
fi
test -f "$B4_DOCKERFILE"
docker build --file "$B4_DOCKERFILE" --tag my-b4-app .
```

Keep `.` as the final build-context argument even when the Dockerfile lives under `.b4/build/`; its `COPY` instructions are rooted at the app.

The generated image is a single-stage `node:24-slim` image. It installs production dependencies with npm, copies the app and `.b4/build`, changes ownership to UID/GID `1000:1000`, runs as that non-root user, exposes port `8000`, checks `/healthz`, and starts `.b4/build/server.mjs`.

## Protect the HTTP runtime

> **Warning:** Do not expose the B4.run Node runtime directly to the public internet. Put reverse-proxy, ingress, or platform authentication in front of the entire service and apply network restrictions so only trusted callers can reach it.

Application middleware gates route-execution requests, but it is not blanket server authentication. Health, thread-management and state endpoints bypass app middleware. The memory-candidate management endpoints also bypass it; they list candidates across namespaces and can approve or delete records. External authentication and network controls must cover these routes as well as Agent Protocol and AG-UI.

## Pass secrets at container run time

Never bake provider keys, database credentials, or other secrets into the image. Keep secret files out of the Docker context and inject values when the container starts:

```bash
docker run --rm \
  --publish 127.0.0.1:8000:8000 \
  --env-file .env \
  my-b4-app
```

The loopback bind is for a local smoke test. In production, keep the container on a private network and publish it only through the authenticated proxy or platform boundary described above.

The Node runtime reads its environment at run time. Document required keys in a safe `.env.example`, but do not commit populated secret files.

In another terminal, smoke-test the generated health endpoint:

```bash
curl --fail http://127.0.0.1:8000/healthz
```

Then exercise one application route through Agent Protocol or AG-UI to validate model credentials, stores, and route wiring—not only process health.

## Replica and persistence limits

The default checkpointer, threads store, permissions store, and memory store are local to the container's filesystem. Even when durable stores are configured externally, the one-run-per-thread gate and cancellation registry are process-local.

Run one replica unless the deployment guarantees thread-keyed sticky routing to the same process **or** supplies distributed per-thread serialization and cancellation routing. Without one of those guarantees, concurrent runs and cancellation requests for the same thread can reach different replicas and bypass B4.run's in-process coordination.

Mount durable storage or configure external stores when thread state must survive container replacement. External persistence alone does not solve the run/cancel coordination requirement.

## Updating an existing install

1. Confirm Node >=24, keep `@b4run/cli` in `dependencies`, and refresh and validate `package-lock.json` with npm.
2. Run `b4 verify`, `b4 test`, and `b4 build --clean` again.
3. Let the generated marker decide placement: B4.run refreshes its marked root Dockerfile and preserves an unmarked user file by emitting `.b4/build/Dockerfile`.
4. Confirm `.b4/build` and `package-lock.json` remain in the build context.
5. Rebuild using the actual emitted path; confirm the build uses `npm ci` rather than its fallback.
6. Repeat the loopback-only `/healthz` and route smoke tests, then verify the production proxy authentication and network restrictions.
