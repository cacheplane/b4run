# Security Architecture

B4.run's route middleware is an execution hook, and it only sees requests that are about to run a route. So put outer authentication and tenant authorization in front of every non-local runtime endpoint. Then layer B4.run's inner agent controls behind it.

## Start at the service edge

Authenticate the caller before the request reaches the B4.run service, and restrict network reachability where you can. The outer layer should:

- reject unauthenticated access on every route,
- apply rate and body-size limits,
- terminate TLS,
- attach verified identity for authorization and audit.

This layer must cover the entire service. Management and health routes never reach `src/middleware.ts`, so protect them here.

## Endpoint coverage

B4.run middleware runs only when a request is about to execute a route. Management surfaces bypass it.

| Surface | Examples | B4.run middleware | Outer auth required |
|---|---|---|---|
| Health | `GET /healthz` | No | Yes on a non-local service. A platform may expose a separately constrained probe path. |
| Thread management | `POST /threads`, `GET /threads/:thread_id`, `DELETE /threads/:thread_id` | No | Yes, with per-thread ownership checks |
| State | `GET /threads/:thread_id/state` | No | Yes, with per-thread ownership checks |
| Cancellation | `POST /threads/:thread_id/cancel` | No | Yes. It controls process-local execution. |
| Agent Protocol execution | `/threads/:thread_id/runs/wait`, `/runs/stream`, and `/resume` | Yes | Yes. Middleware is an additional execution decision. |
| AG-UI execution | `POST /agui/:routeId` | Yes | Yes |
| Memory candidate management | `GET /memory/candidates` and approve/reject routes under `/memory/candidates/:id` | No | Yes. Listing can span namespaces. |

Apply authorization before dispatch, so no request reaches a B4.run handler unauthenticated. The "B4.run middleware" column is about route execution only. When the app has a [thread-access policy](/docs/thread-access), that policy checks per-thread ownership on every thread row above (management, state, cancellation, Agent Protocol execution and AG-UI execution) inside the runtime. It's a second gate behind the outer one. Health and memory-candidate routes are outside it.

## Authorize the tenant, not the identifier

Verified claims answer *who the caller is*. Route parameters, `thread_id`, AG-UI `threadId`, tenant strings in route input and memory namespaces answer *which resource was requested*. Compare the two using records your application keeps.

A sound request path looks like this:

1. Resolve the verified principal.
2. Determine its tenant and roles.
3. Load or check thread ownership.
4. Forward the request.

A thread identifier proves nothing about ownership, even when it's hard to guess. Use the same rule for state, cancellation, deletion, resume and any custom list endpoint.

Memory needs the same care. Candidate management can operate across namespaces, and `memory.resolveScope` receives route and app-root context but never the verified request identity. Don't let model-selected or caller-selected scope strings establish ownership.

## Pass verified identity to tools

For execution routes, outer authentication can forward a signed internal identity header or trusted request context to B4.run middleware. The middleware verifies that trusted value and returns canonical identity through `allow({ ... })`. Tools read it from `ctx.middleware`:

```ts title="src/middleware.ts"
import { allow, defineMiddleware, reject } from "@b4run/sdk"

export default defineMiddleware(async (req) => {
  const identity = await verifyInternalIdentity(req.headers.authorization)
  if (!identity) return reject(401, { error: "Unauthorized" })
  return allow({ userId: identity.userId, tenantId: identity.tenantId })
})
```

The model and the request body must never choose those canonical fields. Keep authorization-sensitive tool arguments separate from verified identity, and have the tool derive tenant filters and credentials from `ctx.middleware`.

## Inner agent controls

After service authentication and tenant authorization, [Access Control](/docs/access-control) composes four narrower controls on each running route:

- [Tool scoping](/docs/tools#scoping-a-routes-tools) limits which tools the model is offered.
- [Permissions](/docs/permissions) gate commands, paths, approved tools, delegations and selected memory writes.
- The [execution sandbox](/docs/sandbox) constrains B4.run's workspace filesystem and shell tools.
- [Guarded delegation](/docs/subagents#delegation-policy) decides whether a subagent receives the delegated input.

These controls cover B4.run's own tools, not your application code. Authored tools execute in the app process unless they isolate themselves. Give their database clients, cloud credentials, network access and filesystem behavior least privilege of their own.

## Secrets and stored data

Keep secrets out of `b4.config.ts` values. The Hono target serializes JSON-compatible configuration into the generated `app.mjs` build artifact. Use platform bindings or environment variables for secrets, and keep emitted artifacts somewhere their contents stay private.

Protect `.env`, provider keys, database URLs, internal identity-signing keys and sandbox credentials with the host's secret system. Scrub verified tokens and sensitive tool arguments from logs and traces.

Postgres rows are plaintext application data unless the app or platform adds encryption. Apply transport encryption, storage encryption, backup protection, database roles, row or schema isolation where it fits, and an audited deletion workflow.

## Target differences

Each build target draws the service edge in a different place:

- **Node** (`b4 start`, `serveRuntime`, generated server). Your reverse proxy or Node host provides blanket auth. B4.run middleware covers execution and AG-UI only. Node can use configured sandboxes.
- **Hono**. Hono or platform middleware must protect the rooted B4.run app. B4.run execution middleware is included in the static manifest. Filesystem workspace and B4.run sandbox features are gated off this target.
- **LangSmith**. The LangSmith platform handles authentication. Generated graph entries don't include B4.run HTTP middleware. Route tool scope and the applicable agent controls remain part of graph materialization.

Check the capabilities of your chosen [Deployment Option](/docs/deployment) before assuming a control carries over unchanged between targets.

## Production checklist

- Restrict network access and require authentication on every endpoint group in the table.
- Map verified principals to application-owned tenant and thread records.
- Reject cross-tenant reads, state access, runs, resume, cancellation and deletion.
- Treat memory-candidate routes as privileged administrative operations.
- Pass canonical identity to tools through trusted middleware context, never model input.
- Run with least-privilege database roles, provider keys, authored tools and sandbox credentials.
- Keep secrets out of generated artifacts and redact them from logs and traces.
- Test middleware-bypassing routes and cross-tenant attempts in the deployed topology.
- Review all of this again whenever the build target or embedding host changes.
