# CLI Reference

B4.run ships a single `b4` binary with fifteen commands: `add`, `build`, `check`, `dev`, `docs`, `eval`, `inspect`, `memory`, `routes`, `run`, `start`, `test`, `threads`, `typegen`, and `verify`. Most commands read `b4.config.ts` from the current working directory or from `--cwd <path>`. `b4 dev` always uses the current working directory.

## Running the CLI

Always run B4.run through the `b4` **bin**: `pnpm exec b4 <command>` (or `npx b4 …` / a `package.json` script). `@b4run/cli` installs the bin into `node_modules/.bin`, and it resolves correctly wherever the package lives.

<Callout type="warn" title="Monorepos: use the bin, not a direct path">
  In an npm/pnpm-hoisted monorepo, `@b4run/cli` usually hoists to the workspace root, so a hardcoded path like `node node_modules/@b4run/cli/dist/index.js` from a sub-package fails to resolve. Run `pnpm exec b4 …` instead. It finds the bin through the workspace's `node_modules/.bin`.
</Callout>

## `b4 check`

Validates the app structure and configuration.

```
b4 check
```

`b4 check` loads `b4.config.ts`, resolves the app root, runs `discoverRoutes`, and parses each route's tool definitions with `discoverToolDefinitions`. It reports:

- A `b4.config.ts` that fails to load.
- An app root `package.json` without `"type": "module"`, reported as `B4_E1006`. B4.run loads `b4.config.ts` and every route `index.ts` as ES modules. Without the field, Node compiles them as CommonJS, and a route exported with `export default agent(...)` is not recognised.
- Any route directory whose `index.ts` has no recognisable export, reported as `B4_E1007` with the file path and the exports it did find. When the module was loaded as CommonJS (a nested `package.json` without `"type": "module"`), the message names that file as the likely cause. Prefix a directory that is not a route with `_` to keep it out of discovery. Every offending entry in the app is reported together.
- Any discovered route whose `index.ts` exports more than one of `agent`, `workflow`, `graph`, `chain`, reported as `B4_E1008` with the file path and the kinds it exported. Every offending entry in the app is reported together. If an app has both `B4_E1007` and `B4_E1008` entries, `b4 check` reports the unrecognised ones first, with a count of the multi-kind ones.
- Any tool file that fails to parse.
- A stale build manifest. When `.b4/build/modules.mjs` exists (written by `b4 build`'s `node` target), `b4 check` compares its routes against the routes on disk. A mismatch (for example, a route renamed after the last build) fails with the missing/extra route ids and a prompt to re-run `b4 build`. When `"hono"` is a configured target, `.b4/build/modules.edge.mjs` is checked the same way. It is a separate artifact with its own copy of every route's static imports, and an app that builds for `hono` **alone** emits no `modules.mjs`. An absent manifest is a no-op, and the edge manifest is skipped when `hono` is not a configured target, so a leftover file from an experiment is not an error.
- An unknown `build.targets` entry and, when `"hono"` is one of them, every feature that target [cannot serve](/docs/deployment/edge#what-the-edge-cannot-serve), reported together as `B4_E1005`. This is the same gate `b4 build` applies, so you learn about all of them before building.

The output is a `B4.run app is valid: N routes discovered.` line followed by a per-route `- <pathname> (<kind>)` summary. On any violation, it exits non-zero with a detailed message.

### Troubleshooting imports

When a route, tool, or config module fails to load with the ESM error `does not provide an export named X`, B4.run prints the offending package plus a likely cause and fix instead of the raw `SyntaxError`. There are two usual causes:

- **An older `@langchain/core` got hoisted.** Run `npm ls @langchain/core` to find the duplicate, then upgrade or dedupe so the installed version satisfies B4.run's peer range (`^1.1.47`).
- **A CommonJS dependency imported with named bindings.** Under B4.run's ESM resolver a CommonJS package only has a default export, so `import { thing } from "x"` fails. Use a default import and destructure instead:

  ```ts
  import pkg from "x"
  const { thing } = pkg
  ```

  Or import the package's ESM build if it ships one.

## `b4 verify`

Runs five checks in one call (`app`, `routes`, `typegen`, `deps`, `runtime`). Run it before `b4 dev`, `b4 start`, or a deploy. A green `b4 verify` means "this app will boot in this environment."

```
b4 verify
b4 verify --json
```

Flags:
- `--cwd <path>`: operate on a different app root.
- `--json`: emit a structured report (`{ status, appRoot, checks, counts }`) instead of human-readable text. A failed check carries `error.message`, plus `error.code` when the failure has an [error-code](/docs/errors) entry (for example `B4_E1006` for an app root that is not an ES module). The same code is rendered as the `[B4_Exxxx] See <docs>` footer in text mode.
- `--env-file <path>`: path to a `.env` file (overrides `b4.config.ts` `env` and the default `./.env`).

The `deps` check covers missing packages and missing env vars (advisory). It is **provider-aware**: it derives the API-key env var from the providers your routes use. An Anthropic-only app is checked for `ANTHROPIC_API_KEY`, an OpenAI app for `OPENAI_API_KEY`, a multi-provider app for the union, and a local Ollama app for none. A missing key is a warning, not a failure, because the key may come from the runtime environment.

The `runtime` check gates **environment readiness**:
- **Node**: asserts the running Node version is at least `24.0.0`, the active LTS line (it bundles npm ≥ 11 and ships `node:sqlite` unflagged). An older version **fails** `verify` with a non-zero exit.
- **Docker**: runs only when `b4.config.ts` configures a sandbox provider. It runs the provider's daemon preflight and **fails** if the daemon is unreachable.

See [Deployment](/docs/deployment) for the recommended workflow.

## `b4 routes`

Lists every route B4.run discovered and its computed pathname.

```
b4 routes
b4 routes --json
```

Output:

```
Discovered 2 B4.run routes in /path/to/app
/research -> src/app/research/index.ts
/admin/users -> src/app/(internal)/admin/users/index.ts
```

Use it to confirm that route groups and dynamic segments parse the way you expect.

## `b4 typegen`

Regenerates `.b4/b4.generated.d.ts` plus per-route `.b4/routes/<routeSlug>/tools.json` and `.b4/routes/<routeSlug>/state.json` manifests.

```
b4 typegen
```

The success log reports route, tool-schema, and stateful-route counts. `b4 build` reads the `tools.json` artifacts to emit LangGraph entries.

Tool input types are compiled with the app's own `tsconfig.json` (nearest to the app root, honoring `extends`, `paths`, and `baseUrl`). When a declared input type resolves to `any` (for example, an import through a path alias the tsconfig does not declare), the command fails and names the tool file and the unresolved type instead of writing an empty schema.

<Callout type="info" title="Run automatically by b4 dev, run, test, and build">
  `b4 dev` runs `typegen` before every child (re)start, so edits to tool signatures or state schemas are picked up on the automatic restart. `b4 run` and `b4 test` run it before executing routes in-process, and `b4 build` runs it before emitting artifacts, so a new or changed tool is bound with its current input schema. Run it yourself after a fresh clone, before CI, or to refresh editor types for `ctx.tools` while the dev server isn't running.
</Callout>

## `b4 build`

Writes deployment artifacts for the configured `build.targets` (default: `["node", "langsmith"]`).

```
b4 build
b4 build --clean
b4 build --out-dir dist/vercel
```

Flags:
- `--cwd <path>`: operate on a different app root.
- `--clean`: wipe `.b4/build/` before writing.
- `--out-dir <dir>`: where the `vercel` target publishes its Build Output tree, resolved relative to the app root (default `.vercel/output`). Overrides `build.vercel.outDir` for this run, and is an error when `"vercel"` is not a configured target.

Emits, per target:
- **`node`**: `.b4/build/server.mjs` (boots `serveRuntime`, the real B4.run runtime) and a hardened `Dockerfile` (written to the app root unless one already exists there, else to `.b4/build/Dockerfile`). Run it with `b4 start` or `docker build`/`docker run`.
- **`langsmith`**: `.b4/build/langgraph.json` plus per-route entry files under `.b4/build/<routeSlug>.ts`, which you hand to LangSmith. The JSON includes `graphs` (keyed by `<routeId>#<kind>`), `dependencies: ["."]`, `env` (`.env.example` if present, else `.env`), and `node_version: "22"`. For `agent` routes, the generated entry imports the default `agent()` descriptor, materializes it as a LangGraph graph, and wires in every discovered route tool.
- **`hono`**: **opt-in.** `.b4/build/app.mjs` (a Hono app around B4.run's web-standard fetch handler, `export default`ed for Cloudflare Workers, Vercel, or Bun), `.b4/build/modules.edge.mjs` (the node-builtin-free module manifest), `.b4/build/stores.mjs` (a per-request Postgres store factory), and a `wrangler.toml` scaffold at the app root (written only if you have none, and never overwritten). Deploy with `wrangler deploy`.
- **`vercel`**: **opt-in.** A [Vercel Build Output API](https://vercel.com/docs/build-output-api) tree: `config.json` and the runtime Node 24 function at `functions/b4.func/` (the self-contained `index.mjs` plus its `.vc-config.json`), serving the same edge subset as `hono`. The tree lands in `.vercel/output`, where Vercel deploys from, unless `build.vercel.outDir` (or `--out-dir`) points elsewhere. Publication swaps the whole directory in one rename, so the directory must not contain the app root. With `build.vercel` configured, the target also copies a static directory into `static/`, bundles each declared function into `functions/<name>.func/`, and orders `routes` as your routes, the filesystem, the runtime, then the SPA fallback. The runtime function is named `b4.func` (or whatever `functionName` says) so it never shadows `static/index.html`. The whole tree is staged, validated, and swapped in atomically. The validator checks that `config.json` is version 3 and still routes to the runtime function, so a composed config with extra routes and functions validates too. The target also reconciles the app-root `vercel.json` with its lifecycle contract: it writes a recommended file (`buildCommand` running `b4 build`, `fluid: true`) when none exists, warns to `.b4/build/vercel.json` when an authored file does not establish that contract, and fails on `fluid: false`. A prebuilt flow (`vercel deploy --prebuilt` from CI, no Vercel Git integration) never runs `buildCommand`, so set `build.vercel.reconcileVercelJson: false` there. The target then neither requires nor touches a committed `vercel.json`, and stops failing on a committed `fluid: false`. Keep Fluid compute enabled in the Vercel project either way, because the function is built for that concurrency model. See [the `vercel` target](/docs/deployment/edge#the-vercel-target).

Choose which targets are emitted with `build.targets` in `b4.config.ts` (e.g. `{ build: { targets: ["node"] } }`). The list replaces the defaults instead of adding to them, so an app deploying to the edge names `{ build: { targets: ["node", "hono"] } }`. Target-specific settings sit beside the list, e.g. `{ build: { targets: ["vercel"], vercel: { outDir: "dist/vercel" } } }`. See [Vercel](/docs/deployment/vercel).

The `hono` target serves a **subset** of B4.run. The build fails with `B4_E1005`, naming every offending config key and file at once, when the app uses the sandbox, `backends.filesystem`/`backends.exec`, a config-supplied store, `toolOutput`, a `workspace/` directory, or route-level long-term memory. The `vercel` target applies the same gate. [`b4 check`](#b4-check) applies the identical gate whenever `hono` or `vercel` is a configured target. See [Edge and Hono](/docs/deployment/edge) and [Vercel](/docs/deployment/vercel).

If you upgrade an app that sets both `toolOutput` and `"hono"`, a build that passed before now fails. Remove the key, or drop `"hono"` from `build.targets`. See [Upgrading](/docs/upgrading#tooloutput-is-now-gated-off-the-hono-target).

See [Deployment](/docs/deployment) for the full bridge.

## `b4 start`

Serves the app in production with the real B4.run runtime (Agent Protocol, AG-UI, and `/healthz`), binding `0.0.0.0:8000` by default.

```
b4 start
b4 start --host 127.0.0.1 --port 3000
```

Flags:
- `--host <host>`: host to bind. Default: `0.0.0.0` (or the `HOST` env var).
- `--port <number>`: port to bind. Default: `8000` (or the `PORT` env var).

This is what the `node` build target's generated `Dockerfile` runs (`CMD ["node", ".b4/build/server.mjs"]`), and it's the only server that runs the [execution sandbox](/docs/sandbox) in production. See [Node and Docker](/docs/deployment/node).

## `b4 run`

Executes a single route invocation with JSON stdin/stdout.

```
echo '{"messages":[{"role":"user","content":"Hello"}]}' | b4 run '/research'
```

Flags:
- `--cwd <path>`: operate on a different app root.
- `--url <url>`: run against a live dev server instead of the in-process runtime.

The route argument can be the parameterized id (e.g. `/research`) or the relative route entry file path (e.g. `src/app/research/index.ts`). Dynamic segment values come from the JSON input. When `--url` is set, `b4 run` POSTs to `/threads/<t-cli-uuid>/runs/wait` with `{ route: "<routeId>#<kind>", input }`.

Without `--url`, `b4 run` regenerates the `.b4/` typegen output first, so a tool you just added or changed is bound with its current input schema. You don't need to run `b4 typegen` first. If regeneration fails, for example because a tool's input type cannot be resolved, `b4 run` prints a warning on stderr and still runs the route with the schemas already on disk.

<Callout type="tip" title="Quote the path">
  Route paths containing `(`, `)`, `[`, or `]` should be quoted in shell so they aren't expanded.
</Callout>

## `b4 test`

Runs every colocated `run.test.ts` scenario in the app.

```
b4 test
b4 test src/app/(public)/hello
```

Flags:
- `--cwd <path>`: operate on a different app root.

The optional positional `[path]` argument narrows the discovered scenario set to a subdirectory. To target a live dev server, add `.server(url)` to that scenario's builder chain inside `run.test.ts` (there is no command-level `--url` flag on `b4 test`). Before running in-process scenarios, `b4 test` regenerates the `.b4/` typegen output the same way `b4 run` does. Exits non-zero on any failure with a diff per mismatched scenario. See [Testing](/docs/testing) for scenario authoring.

## `b4 eval`

Runs every colocated `*.eval.ts` over its dataset and reports per-case scores, then gates on the aggregate.

```
b4 eval
b4 eval src/app/chat
b4 eval --live
b4 eval --record
b4 eval --json
```

Flags:
- `--cwd <path>`: operate on a different app root.
- `--live`: run against the real model (requires `OPENAI_API_KEY`). Never use it in CI.
- `--record`: record real-model responses into sibling fixture files (requires `OPENAI_API_KEY`). Never use it in CI. Mutually exclusive with `--live`.
- `--json [file]`: write a JSON report. Defaults to `.b4/eval-report.json`.

The optional positional `[path]` narrows discovery to a subdirectory. By default each case replays its aimock fixtures (deterministic and CI-safe). `--live` calls the real provider for local prompt tuning. `--record` captures real-model responses as committed fixture files that plain `b4 eval` replays. A failing gated eval exits non-zero, so CI fails when quality drops below the bar. Informational evals (no `gate`/`threshold`) never affect the exit code. See [Evals](/docs/evals) for authoring.

## `b4 dev`

Starts the local runtime with hot reload and the [Agent Protocol (AP) HTTP endpoints](/docs/dev-server/agent-protocol). The bind address is fixed at `127.0.0.1`.

```
b4 dev
b4 dev --port 3001
```

Flags:
- `--port <n>`: HTTP port. Default: dynamically allocated. Pass `--port` for a stable address.
- `--env-file <path>`: path to a `.env` file (overrides `b4.config.ts` `env` and the default `./.env`).

Because the default port is dynamic, pass an explicit `--port` (or read the port `b4 dev` prints on startup) before you copy a `curl` example.

If `LANGSMITH_API_KEY` is present in the loaded environment and `LANGCHAIN_TRACING_V2` is not already set, `b4 dev` automatically enables LangSmith tracing by setting `LANGCHAIN_TRACING_V2=true`. Set `LANGCHAIN_PROJECT` to control which project receives the traces. See [Observability](/docs/observability) for tracing and [Agent Protocol](/docs/dev-server/agent-protocol) for the protocol reference.

## `b4 memory`

Inspects and manages the app's [long-term memory](/docs/memory/browse) store (the
typed records the agent writes with its generated `remember` tool). Use it to
review and promote the `candidate` writes that the default `memory: { writes: "candidate" }`
config holds back from `recall`.

```
b4 memory list
b4 memory search <query>
b4 memory inspect <id>
b4 memory approve <id>
b4 memory reject <id>
b4 memory forget <id>
b4 memory prune [--cap <n>] [--namespace <prefix>]
b4 memory consolidate [--dry-run] [--namespace <prefix>] [--model <id>] [--provider <id>] [--max-batches <n>]
b4 memory reflect [--dry-run] [--namespace <prefix>] [--model <id>] [--provider <id>] [--max-batches <n>]
```

Subcommands:
- `list`: list pending candidate records.
- `search <query>`: list candidates whose content or namespace matches `<query>`.
- `inspect <id>`: print one record as formatted JSON.
- `approve <id>`: promote a candidate to an `active` record so `recall` surfaces it.
- `reject <id>`: drop a candidate without promoting it.
- `forget <id>`: delete a record by id.
- `prune`: run [episodic retention](/docs/memory/episodes#retention) manually:
  delete expired records (TTL) and enforce the per-namespace episode cap.
  `--cap <n>` overrides the cap for this pass; `--namespace <prefix>` scopes
  the pass to namespaces matching the prefix.
- `consolidate`: run [distillation](/docs/memory/distillation)'s compaction
  pass: group old episodic records per (namespace, ISO week), summarize each
  group with one model call, then supersede the sources and stamp them with a
  TTL so `prune` reaps them later.
- `reflect`: run distillation's insight pass: derive durable insights from each
  namespace's records newer than its watermark. Insights are written as
  `candidate` by default. Approve them with `approve <id>` or the Inspector.

`consolidate` and `reflect` share the same flags. Below the configured
thresholds, both print one line, exit `0`, construct no model, and need no API
key. That makes the cron recipe (`b4 memory consolidate && b4 memory reflect`)
safe to run nightly on any app. Their flags:

- `--dry-run`: report the plan without making any model call.
- `--namespace <prefix>`: scope the pass.
- `--model <id>` / `--provider <id>`: override `memory.distill`.
- `--max-batches <n>`: cap the work (and spend) for one invocation.

These are the only `b4 memory` subcommands that spend model tokens. See [Distillation](/docs/memory/distillation) for the full configuration
block.

Flags:
- `--cwd <path>`: operate on a different app root.

## `b4 inspect`

Opens the [B4.run Inspector](/docs/inspector), a localhost-only browser UI for
browsing, searching, and approving the app's [long-term memory](/docs/memory/browse)
records.

```
b4 inspect
```

The inspector binds to `127.0.0.1` on a free port and prints the URL to open.

Flags:
- `--cwd <path>`: operate on a different app root.
- `--port <number>`: bind the inspector to a stable localhost port.
- `--env-file <path>`: path to a `.env` file (overrides `b4.config.ts` `env` and the default `./.env`).

## `b4 add`

Fetches a blueprint (an agent-facing integration guide) and prints it to stdout so you can hand it to your coding agent.

```
b4 add                 # list available blueprints, grouped by category
b4 add pgvector        # print the pgvector blueprint
b4 add <url>           # fetch a third-party blueprint from any URL
```

`b4 add` only prints the guide. Your agent applies the changes, and you review them. Set `B4_BLUEPRINTS_URL` to point at a self-hosted catalog instead of `b4.run`.

See [Blueprints](/docs/blueprints) for authoring and catalog details.

## `b4 docs`

Prints the **bundled, version-matched** B4.run docs that ship inside the installed
CLI, so a coding agent (or you) can read the docs for the exact version in use
without a network round-trip. With no topic, it lists the available topics and the
index. With a topic, it prints that doc to stdout.

```
b4 docs
b4 docs README
b4 docs cli
```

The optional positional `[topic]` selects a single doc by slug (with or without
the `.md` suffix). An unknown topic exits non-zero and lists the available
topics. Running from a source checkout requires the CLI to be built first
(`pnpm --filter @b4run/cli build`) so the bundled docs exist.

## `b4 threads`

Inspects and reattaches to Agent Protocol threads on a running B4.run server.

```
b4 threads tail <thread-id>
b4 threads tail <thread-id> --url http://127.0.0.1:3000
b4 threads tail <thread-id> --header "authorization: Bearer $TOKEN"
b4 threads tail <thread-id> --json
```

`tail` rejoins a thread through
[`GET /threads/:thread_id/runs/stream`](/docs/dev-server/agent-protocol) (the
reattach endpoint). Use it to recover after a disconnect, a reload, or a lost
terminal. It prints a snapshot first, then follows whatever comes next:

- When a turn is **streaming in that server process**, the snapshot carries the
  committed transcript plus the turn's output so far, and the command then tails
  live frames until the turn emits `done`.
- When **no turn is live** there, the snapshot is the durable one (the latest
  checkpoint plus any parked human-in-the-loop prompts), and the command exits
  immediately. This path works across restarts and replicas because it is
  checkpoint-backed.

The header line reports `status`, whether the attach is `live`, the turn's
`run_started_at`, and the checkpoint `anchor`. Comparing `run_started_at` across
reattachments tells you whether a *different* turn now owns the thread; `anchor`
correlates a resumed turn back to the run it continues.

Attaching never cancels anything and never takes the thread's run slot, so it is
safe to tail a thread someone else is driving. To stop a run, use
`POST /threads/:thread_id/cancel` instead.

Flags:
- `--url <url>`: base URL of the running B4.run server (default
  `http://127.0.0.1:3000`).
- `--header <name: value>`: extra request header, repeatable. Use it when the
  server's middleware authenticates the thread's route.
- `--json`: print raw SSE frames as JSON, one per line, instead of rendered
  text.

Exit codes follow the table below: `1` when the stream ends without a terminal
`done` frame or the server detaches the viewer (the per-thread viewer cap, or a
consumer too slow to keep up; reconnect for a fresh snapshot), and `2` when the
server is unreachable, the thread does not exist, or the thread has never run
and so has no route identity to authorize against.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | Validation failure (e.g. `b4 check`) or scenario failure (e.g. `b4 test`) |
| 2 | Configuration / runtime error (missing `b4.config.ts`, bad `appDir`, scenario load failure) |

Non-zero exit codes from underlying tools (Commander, child processes) may be propagated unchanged.
