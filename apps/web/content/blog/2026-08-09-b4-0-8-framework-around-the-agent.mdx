Building an agent starts with a model and a few tools. Building an application around that agent brings another set of questions. How do we test its behavior? Which actions require approval? What should it remember? How does a browser display its progress?

B4.run's route conventions give those pieces a place to live. The releases from 0.5 through 0.8.21 added more of the behavior around them, including evaluations, tool permissions, long-term memory, and production runtime options.

Let's break these down using a support assistant as our example. The assistant can look up an order, research a policy, and prepare a reply. We will look at what each framework capability contributes to that application.

**Version note:** This is a roundup through 0.8.21, rather than a list of features introduced in that single release. The examples use the current `@b4run` package names, introduced in 0.8.27. Follow the linked upgrade guide for a current installation instead of installing those package names at 0.8.21.

## Goals

We want our support application to:

1. Check its behavior against repeatable scenarios.
2. Limit tool access and request approval where needed.
3. Delegate a specific task to a specialist agent.
4. Retain useful information across conversations.
5. Connect to a browser and run outside the development server.

You can add these capabilities as you need them. A small agent does not need every one of them on its first day.

## Evaluate agent behavior

A unit test can tell us that `lookupOrder()` returns the expected order. It does not tell us whether a model will choose that tool when a customer asks about a delivery.

An **evaluation**, or **eval**, runs a set of scenarios and scores their results. The scenarios form a **dataset**. A **scorer** checks one aspect of the result, such as required text, a tool call, or a budget. A **gate** decides whether the collected scores meet our chosen threshold.

### Start with a small eval

An eval lives beside its route under `evals/*.eval.ts`. Here is a deliberately small example for a `/support` route:

```ts
// src/app/support/evals/greeting.eval.ts
import { contains, defineEval } from "@b4run/evals"
import { script } from "@b4run/testing"

export default defineEval({
  name: "support greeting",
  dataset: [
    {
      name: "offers help",
      input: "hello",
      fixtures: script().user("hello").replies("Hi! How can I help?"),
    },
  ],
  scorers: [contains("help", { threshold: 1 })],
  threshold: 1,
})
```

A few things to note:

1. The file's location associates it with the support route.
2. `dataset` contains one scenario with a user input and a scripted model response.
3. `contains()` checks whether the final text contains `help`.
4. The outer `threshold` sets the mean score required for the eval to pass.

This example teaches the API; a greeting alone is not a useful quality bar for a support application. Add scenarios for the work the agent should perform, including missing orders, ambiguous requests, and service failures.

### Replay and live runs

By default, `b4 eval` replays model fixtures. Our tools, prompts, capabilities, and state execute, while the model response comes from the fixture. This makes the scenario repeatable in CI.

There is an important limit: a passing replay does not demonstrate that a live model will make the same decision. We supplied its response. Use `b4 eval --live` to measure real model behavior, and `--record` to capture responses for later replay. Both make provider calls and incur their associated cost.

Scorers run after the agent finishes. If a scorer uses another model to judge the answer, that model call also needs a fixture or mock for an offline CI run.

For smaller checks, `@b4run/testing` includes harnesses for agents, tools, middleware, workspaces, and protocol behavior. Choose the harness for the part you need to exercise. See [Evals](/docs/evals) and [Testing agents](/docs/testing-agents) for complete examples.

## Control tool execution

Our support agent might be allowed to look up orders automatically, while issuing a refund requires a person to approve the request.

There are three separate decisions here:

| Question | Framework mechanism |
| --- | --- |
| Should the model have access to this tool? | Tool scoping with allow and deny rules |
| Should this particular call execute? | Argument constraints and approval rules |
| Where will the approved operation run? | The host environment or a configured sandbox |

Let's look at the first two using a route configuration:

```ts
import { agent } from "@b4run/sdk"

export default agent({
  model: "gpt-5-mini",
  systemPrompt: "Help customers with their orders and refund requests.",
  tools: {
    deny: ["deleteAccount"],
    approve: ["issueRefund"],
  },
})
```

The `deny` rule removes `deleteAccount` from the tools available to this agent. The `approve` rule pauses an `issueRefund` call for a decision before executing it. These names refer to tools implemented by the application; declaring a name does not create the tool.

Argument constraints can inspect the proposed input as well. For example, an application may require additional review for a refund above a certain amount. The constraint can allow the call, reject it with a reason, or request approval.

The tool implementation still needs to verify the authenticated customer's access to the order. Model instructions and route parameters do not replace authorization in application code.

### Isolate filesystem and shell work

A workspace gives file operations a configured root directory. Permission checks govern shell commands and access outside that workspace. If an approved operation runs on the application host, those checks do not turn it into an isolated process.

A **sandbox** provides a separate execution environment for filesystem and shell work. B4.run has Docker and Kubernetes providers for this purpose.

The Docker provider uses a non-root user, drops Linux capabilities, prevents privilege escalation, and makes the root filesystem read-only by default. Network restrictions depend on the selected mode: deny-network blocks egress, while an allow-mode host denylist is best-effort. Kubernetes network enforcement depends on a policy-capable network plugin.

Sandbox lifecycle matters too. `release()` drops warm compute while retaining the thread's volume and workspace. `destroy()` removes both the compute and persisted workspace data. For a conversation that will continue later, those operations have different consequences.

The [Access Control](/docs/access-control) and [Sandbox](/docs/sandbox) guides show how to configure each layer.

## Delegate a task

A **subagent** is an agent that handles a bounded task for another agent. Our support assistant could delegate policy research, then use the findings to prepare its response.

The parent can register children by name and declare when each may run:

```ts
import { agent } from "@b4run/sdk"
import researcher from "./subagents/researcher/index.js"
import writer from "./subagents/writer/index.js"

export default agent({
  model: "gpt-5-mini",
  systemPrompt: "Coordinate research and writing for support requests.",
  subagents: { researcher, writer },
  delegation: {
    default: "deny",
    rules: {
      researcher: { action: "allow" },
      writer: { action: "approve", reason: "Approve draft generation." },
    },
  },
})
```

First, we import two child descriptors from their route files. Each of those files exports its own `agent()` declaration with instructions and tools for that task.

Next, the keys in `subagents` give the children the names the parent can request. The delegation rules use those same names.

Finally, `researcher` is allowed to run, while dispatching `writer` requires approval. This approval is for starting the writer; publishing or sending its output would need its own application controls.

The policy belongs to this parent. Allowing its research child does not also authorize every child that the researcher might call. Delegated executions have separate saved execution state, and an approval requested by a child returns through the root conversation so the client can resume it there.

For applications upgrading from older registration forms, the current API requires a keyed `subagents` object. Array registration and old scalar resume bodies need migration. The [Subagents guide](/docs/subagents) covers the full configuration and resume behavior.

## Remember information across conversations

Conversation state helps continue the current thread. Long-term memory retains records that may be useful in a later thread.

For example, a support assistant may need to remember a reviewed preference about how an organization receives reports. A route declares the shape of those records in `memory.ts`:

```ts
// src/app/support/memory.ts
import { defineMemory } from "@b4run/sdk"
import { z } from "zod"

export default defineMemory({
  kind: "semantic",
  scope: ["workspace", "route"],
  identity: ["subject", "attribute"],
  schema: z.object({
    subject: z.string(),
    attribute: z.string(),
    value: z.string(),
  }),
})
```

Let's review the declaration:

- `kind: "semantic"` describes factual records.
- `scope` places the collection in the workspace and route namespace. This example is not a tenant authentication boundary.
- `identity` identifies which fields describe the same fact, such as an organization and its preferred report format.
- `schema` declares the data written with each record. Type generation carries this shape into the agent's `remember` tool, and runtime validation checks writes again.

### Review before recall

Agent-authored writes become candidates by default. A candidate is stored for review but is excluded from normal recall until approved. You can inspect and approve candidates through the CLI or local Memory Inspector.

This matters because an agent can misunderstand a conversation. Saving its interpretation should not automatically make that interpretation trusted context for later answers.

The default SQLite store ranks recall using keywords, recency, and confidence. Hybrid recall can also use vectors, which help find related meaning when wording differs. `@b4run/memory-pgvector` provides a shared Postgres option for the long-term collection.

### Record events separately

Episodic memory records events: what happened during a run. The runtime recorder is optional and uses retention limits. Two explicit commands can process older records:

- `b4 memory consolidate` compacts older episodes.
- `b4 memory reflect` derives insights for review.

These commands do not run automatically. Decide when to run them based on the application's needs and model cost. The [Memory guide](/docs/memory) explains record types, review, and recall; the [Inspector guide](/docs/inspector) covers the local development interface.

## Connect a browser client

A browser needs more than the agent's final answer. It may need to show text as it arrives, display tool activity, and ask the user to approve an operation.

**AG-UI** is an event protocol for that interaction. B4.run maps runtime activity into AG-UI events, preserving tool-call ids so the browser can associate a result with the call that produced it. The reference web client uses CopilotKit.

The thread-scoped Agent Protocol API remains available for direct clients. A typical interaction is:

1. Create a thread for the conversation.
2. Start a run under that thread and read its result or stream.
3. If execution pauses for approval, display the pending requests.
4. Resume the root thread with decisions addressed to every pending interrupt id.

The ids matter when more than one operation is waiting for a decision. A single “yes” cannot safely identify which requests it answers.

Both client paths reach the same route code and configured runtime stores. See [AG-UI and Web Clients](/docs/ag-ui) and [Dev Server](/docs/dev-server) for the request formats.

## Deploy the application

`b4 build` can generate a Node server and Dockerfile. `b4 start` runs the B4.run production runtime directly. These paths support its HTTP APIs, middleware, tool rules, permissions, and configured sandbox.

If the host has an ephemeral filesystem, or several instances need the same saved records, `@b4run/postgres-storage` stores checkpoints, threads, and permission grants in Postgres. These are runtime records; typed long-term memory uses its separate memory store.

Shared records do not solve every coordination problem. Cancellation and the one-run-per-thread guard remain process-local, so applications running several replicas need to account for that behavior.

The optional Hono target supports a narrower edge environment. It excludes capabilities that need local filesystem or shell execution, and its qualification uses local workerd rather than a live Cloudflare deployment. [B4.run at the edge](/blog/b4-at-the-edge) explains that design and its limits.

## Upgrade an existing application

Use Node.js 24 or later, and keep direct `@b4run/*` dependencies on the same exact release. The framework is pre-1.0, and 0.8 patch releases have included breaking API changes.

For an upgrade:

1. Read the [Upgrading guide](/docs/upgrading) and the intervening release notes.
2. Update all direct B4.run dependencies together to the chosen published version.
3. Run `pnpm exec b4 verify` to check the application.
4. Run the route tests and evals.
5. Exercise the deployment target and approval flows the application actually uses.

For a new project, follow [Getting Started](/docs/getting-started). The starter provides a working application with consistent package versions.

## Conclusion

An agent becomes useful inside an application when we can test its behavior, control its actions, retain appropriate context, and connect it to users.

These releases give us more of those pieces around the route. Start with the part your application needs next: a repeatable eval, an approval before a tool call, or a memory collection you can review. Then test the complete interaction so you understand what the framework handles and what remains application code.
