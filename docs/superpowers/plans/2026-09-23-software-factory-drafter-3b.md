# Software factory drafter for real (sub-project 3b): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The intake that 3a proved with a scripted fake runs for real: a drafter app in its own process and fixed image reads a wide read-only capture of the repository at the work order's pin and writes `draft/`; the controller reads only `draft/` by re-rooting the byte channel; the controller addresses one builder process per target and one drafter process through a worker map; the builder resolves its workspace per work order from thread metadata; and a target is prepared per pin, so verification runs at the pin the work order was created against. Proven with a two-thread run of the real builder app, one real intake turn against the wide capture, and the existing Docker lanes.

**Architecture:** Two halves, each a PR. **Half A (Tasks 1 to 5): the drafter and the worker map.** A new app `examples/software-factory/drafter/` with one `intake` agent route, a `node:24-slim` image pinned by digest, no baseline, non-interactive permissions, and a resolver that reads `metadata.factoryWorkOrderId` and loads a per-work-order manifest the controller writes before it creates the thread. The controller's reader gains a `root` option so the drafter thread is inspected from `/workspace/draft`, which is what makes the wide capture (executables, a binary, over the 16 MiB inspection cap) readable at all. The controller's config becomes a map of workers: one per target plus the drafter, with today's two variables kept as a single-target shorthand. **Half B (Tasks 6 to 9): the builder per work order and per-pin images.** The builder's resolver becomes per work order through the same manifest mechanism, `target.json` records images per pin, `target:prepare --pin` builds one, a generated task carries its pin, `loadTask` threads it into `loadTarget`, and an unprepared pin is a named block. Cut a PR after Task 5; Half B rebases on it.

**Tech Stack:** TypeScript, vitest, zod, `@b4run/cli` (`serveRuntime`, the resolver form), `@b4run/workspace` (`captureWorkspaceDefinition`, `inspectWorkspace`), `@b4run/sandbox` (`dockerSandbox`), `@b4run/testing` (`createAimock`), Docker, the controller's fakes.

**Spec:** `docs/superpowers/specs/2026-09-21-software-factory-rung3-design.md` §5 (as landed), §6.4, §6.7, the "Decisions of 2026-09-22" blockquote, §9. Survey of 2026-09-23 (in this plan's Task 1 notes) is the code basis. Deviations from the spec's text this plan makes, recorded as "As landed" notes in Task 9: the drafter's image is the plain `node:24-slim` base by digest, not a built image (it runs no commands); `repo/` is NOT write-fenced (inside-workspace writes are always allowed by the permission gate; the re-rooted read is the boundary, and §9's wording changes to say so); the generated `task.json` carries `pin` so every catalog lookup is pin-correct with no signature churn; `environmentIdentity` folds the pin.

**Standing rules:** `nvm use 24`. Never bare `git stash`; never bare `biome check --write` at the root. Commit after every task with the trailer; the controller's unit suite, typecheck and lint green at every commit; the drafter app's own `check`/`build`/`test`/`typecheck`/`lint` green from Task 1 on. Docker lanes run in Tasks 5 and 9. `C/` = `examples/software-factory/controller/`, `S/` = `examples/software-factory/server/`, `D/` = `examples/software-factory/drafter/`. Worktree `.claude/worktrees/factory-intake-3b`, branch `blove/software-factory-intake-3b` (off `blove/software-factory-intake`; rebase onto main once PR #794 merges). Subagents' Edit/Write refuse a sibling worktree: shell edits.
