# Long-term Memory

Add a route-local `memory.ts` when an agent needs durable, typed records rather than another prompt file. It declares the record shape, kind, namespace dimensions, and identity.

## Declare a collection

Place `memory.ts` beside the agent route:

```ts title="src/app/support/memory.ts"
import { defineMemory } from "@b4run/sdk"
import { z } from "zod"

export default defineMemory({
  kind: "semantic",
  scope: ["workspace", "route"],
  identity: ["subject", "attribute"],
  schema: z.object({
    subject: z.string(),
    attribute: z.string(),
    value: z.string(),
  }),
})
```

- `kind` is `semantic`, `episodic`, `reflection`, or `procedural`.
- `scope` is a subset of `workspace`, `route`, `tenant`, `user`, and `agent`. It determines the namespace dimensions that isolate records.
- `schema` validates `remember.data` at typegen time and again at runtime.
- `identity` selects fields used to reconcile semantic facts. It defaults to `subject` and `predicate`.

`semantic`, `episodic`, and `reflection` writes are wired today. `procedural` exists in the type system only, so `remember` rejects `procedural` writes.

## Scope is addressing, not authentication

The runtime constructs the route and workspace dimensions. Additional dimensions can come from `memory.resolveScope`:

```ts title="b4.config.ts"
export default {
  memory: {
    resolveScope: ({ routePath, appRoot }) => {
      console.info("resolving memory scope", { routePath, appRoot })
      return { agent: process.env.B4_AGENT_SLOT ?? "primary" }
    },
  },
} satisfies import("@b4run/core").B4Config
```

B4.run keeps only the dimensions the route declares, so this example needs `agent` in the `scope` of `memory.ts`.

The callback receives only `routePath` and `appRoot`. It does not receive verified identity or middleware context. Never derive a tenant from an untrusted route parameter, thread id, or request body. If a namespace needs a verified tenant or user, add your own wiring that authenticates that identity, and test cross-tenant isolation. See [Persistence and Tenancy](/docs/persistence#tenant-ownership).

## Generated `recall` and `remember` tools

Typegen adds generated `recall` and `remember` tools to any agent route with a `memory.ts`:

- `recall({ query?, kind?, tags?, limit?, since?, until? })` reads active in-scope records. [Recall and Retrieval](/docs/memory/retrieval) covers ranking and time windows.
- `remember({ data, content, tags?, confidence? })` validates the typed data and stores a human-readable `content` string. It's omitted when `memory.writes` is `"off"`.

The model-facing data type follows your Zod schema, and runtime validation still runs when the model calls the tool.

## Record identity and write behavior

Semantic IDs are derived from the namespace and serialized data. With automatic writes, B4.run compares the configured identity fields against active semantic records:

| Match | Result |
|---|---|
| No identity match | Append a new active record |
| Same identity and same data | Update content, confidence, tags, and `updatedAt` on the existing record |
| Same identity and different data | Write the new record and supersede the old one |

Episodic and reflection records always append. Their IDs salt the namespace and data with the write timestamp, so repeated writes normally stay distinct. The store upserts by ID, so identical namespace and data written in the same millisecond get the same ID and overwrite each other.

Each record carries `createdAt` and `updatedAt`. Append kinds also use the request timestamp as `effectiveAt`. The model can supply content, tags, and confidence. It cannot set identity or timestamp fields.

## Write governance

Let's configure the generated write tool in **b4.config.ts**:

```ts title="b4.config.ts"
export default {
  memory: {
    writes: "candidate",
  },
} satisfies import("@b4run/core").B4Config
```

| Mode | Behavior |
|---|---|
| `candidate` | Default. Writes are stored for review and stay out of normal recall until approved. |
| `auto` | Adds and reconciliations become active immediately. |
| `ask` | Adds and idempotent updates act like `auto`. A semantic supersede goes through the memory permission gate. |
| `off` | The generated `remember` tool is absent. |

Approving a semantic candidate reconciles its identity before activation. Episodic and reflection candidates just activate, because append records can't contradict earlier events or insights.

### `ask` mode

`ask` gates only the semantic contradiction branch. A new fact with no matching identity, or one that repeats the same data, writes without a prompt. Episodic and reflection writes never trigger the supersede gate.

In headless/non-interactive mode, an unknown decision is allowed, so `ask` behaves like `auto`. And without a permissions store, the supersede is also allowed. Explicit deny rules are still honored.

This makes `ask` a supervision affordance, not a security boundary. When a write must be prevented, use an explicit deny policy and application authorization. Keep in mind that an interactive decision lives in one process, so it won't authorize anything across replicas.

## Reviewing candidates

During development, you can work the queue from the CLI:

```bash
b4 memory list
b4 memory approve <id>
b4 memory reject <id>
```

The local runtime also exposes list, approve, and reject routes for candidates. They have no authentication of their own, so put them behind your own authentication and tenant authorization before exposing them. For a broader admin surface, follow [Browse and Manage Memory](/docs/memory/browse).

## Stores and lifecycle

The default Node store is SQLite at `.b4/memory.sqlite`. Set `memory.store` to use another backend. `@b4run/memory-pgvector` provides a shared Postgres store with vector candidate retrieval. It stays separate from the checkpoint, thread metadata, and permissions stores.

Long-term memory outlives the thread. Call the store's `delete(id)` to remove one record, and `prune({ now, namespacePrefix?, cap? })` to remove expired records and enforce episodic caps. Account deletion, retention, backups, and audit across every namespace-bearing store are your application's job.

## Configuration

You set the store, governance mode, ranking, embeddings, episode recording, distillation, and scope resolution independently. Here are the first three:

```ts title="b4.config.ts"
import { sqliteMemoryStore } from "@b4run/memory"

export default {
  memory: {
    store: sqliteMemoryStore({ path: ".b4/memory.sqlite" }),
    writes: "candidate",
    recall: { candidatePool: 256 },
  },
} satisfies import("@b4run/core").B4Config
```

A custom store owns its search behavior and ignores the built-in SQLite ranker options. Keep provider credentials and application identity out of model-authored scope data.

## Testing

Seed known records without asking a model to call `remember`:

```ts title="test/support-memory.test.ts"
import { basename } from "node:path"
import { fileURLToPath } from "node:url"
import { sqliteMemoryStore } from "@b4run/memory"
import { serializeNamespace } from "@b4run/memory/namespace"
import { seedMemory } from "@b4run/testing"

const appRoot = fileURLToPath(new URL("..", import.meta.url))
const store = sqliteMemoryStore({ path: ":memory:" })

await seedMemory(store, [{
  id: "customer-locale",
  namespace: serializeNamespace({
    workspace: basename(appRoot),
    route: "/support",
  }),
  kind: "semantic",
  content: "Customer prefers French replies",
  data: { subject: "customer", attribute: "locale", value: "fr" },
  status: "active",
}])
```

This builds the same workspace value the runtime uses: the basename of the app root, not the full filesystem path. The `:memory:` database is process-local, so there's no file to clean up.

Test the namespace, schema rejection, candidate approval, semantic update/supersede behavior, and retention separately. Fix timestamps in store tests so recency and expiry don't depend on the wall clock.

### Verifying against a real model

Once the deterministic tests pass, add a narrow integration test that asks the configured model to recall a distinctive seeded fact and, separately, to propose a write. Assert on the tool event or stored record, not the model's wording. Keep candidate mode on unless the test exercises automatic writes.

## What's deferred

A few things aren't built yet:

- The `procedural` kind is typed but has no generated write path.
- Nothing migrates records between namespace schemes.
- There's no account-erasure transaction across stores.
- `resolveScope` gets no verified request principal. A declared scope names the dimensions, and your application supplies the identity.
